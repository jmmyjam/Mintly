# Mintly — Handoff Document

*Last updated: July 21, 2026*

A Pokemon TCG portfolio tracker: search cards, view live market prices, and track a collection's value over time.

## Stack

| Layer | Tech |
|---|---|
| Backend | FastAPI, PostgreSQL, SQLAlchemy, JWT auth (python-jose + passlib/bcrypt) |
| Frontend | React 19, TypeScript, Vite, React Router 7, Recharts |
| Data source | [Pokemon TCG API](https://pokemontcg.io) (prices via TCGPlayer); [TCGCSV](https://tcgcsv.com) fills TCGplayer prices for cards it lacks; eBay sold listings as last resort |

## Running locally

**Backend** (from `Backend/`):
```bash
source venv/bin/activate
alembic upgrade head                 # apply DB migrations (needed on first run / after pulling schema changes)
uvicorn app.main:app --reload        # http://localhost:8000, docs at /docs
pip install -r requirements-dev.txt  # test deps (pytest, httpx)
pytest tests/ -q                     # backend tests — offline (in-memory SQLite + fake upstream API)
```
Requires a `.env` in `Backend/` (not committed):
```
DATABASE_URL=postgresql://username@localhost:5432/mintly
SECRET_KEY=...
POKEMON_TCG_API_KEY=...
CORS_ORIGINS=http://localhost:5173   # optional — comma-separated allowed frontend origins (this is the default)
RATE_LIMIT_TRUST_FORWARDED=1         # optional — ONLY behind a reverse proxy: keys rate limits on X-Forwarded-For
```

**Frontend** (from `Frontend/mintly/`):
```bash
npm install
npm run dev                          # http://localhost:5173
npm run build                        # type-check + production build
npx eslint src/                      # lint (strict react-hooks rules enabled)
```
The API base URL comes from `VITE_API_BASE` (see `.env.example`; baked in at build time). Unset it for local dev — it defaults to `http://localhost:8000`.

## Architecture

### Backend files
- `app/main.py` — app assembly, and the uvicorn target (`app.main:app`): creates the FastAPI app, configures CORS (origins from `CORS_ORIGINS` env var, comma-separated; defaults to `http://localhost:5173`), and includes the auth/portfolio/cards routers.
- `app/routers/cards.py` — card/set endpoints + smart search, served **catalog-first**: once a complete crawl has stamped the sync marker (`catalog_meta.last_full_sync` — checked per request via `card_catalog.is_synced`), `/search`, `/cards`, and `/sets/{set_id}/cards` are answered straight from the `card_catalog` table (single-digit ms, no upstream call), and `/cards/{card_id}` always prefers a catalog row when one exists. Catalog answers order newest-sets-first (release date desc, then natural card-number order) and match names as case-insensitive substrings. The upstream proxy below remains the fallback for: an unsynced catalog (fresh DB), zero-result queries (typos, or sets newer than the last crawl), unknown single cards, and sets the catalog holds incompletely (`set_count` < the sets list's `total` — a half-crawled set must never serve confidently-short pages); fallback results are upserted back into the catalog (`_upsert_results`, best-effort), so new sets converge before the next crawl. **Stale prices refresh in the background**: a catalog row whose `price_updated_at` is past `card_catalog.PRICE_TTL` (6h) is served instantly anyway — `/cards/{card_id}` adds `refreshing: true` (the frontend re-polls on it) and list pages batch their stale ids — while `_refresh_prices_in_background` re-fetches via one `id:"…" OR …` upstream call (`refresh_card_prices` is the synchronous, testable core; per-id-set dedupe through `_refreshing`; a failed refresh just leaves the row stale for the next view). All catalog access is wrapped best-effort: a DB hiccup drops to the proxy, never a 500. The proxy path keeps its response cache (covers searches, single-card lookups, and the sets list, keyed per query+page). Cache entries are **stale-while-revalidate**: fresh for 6h (`_CACHE_TTL`), then served immediately while one daemon thread per key re-fetches in the background (`_refresh_in_background`; a failed refresh leaves the stale entry for the next attempt); past 24h (`_STALE_TTL`) the entry is dead and the fetch is synchronous again. Every cache write is also **mirrored to disk** (`Backend/.cache/cards`, gitignored; `CARD_CACHE_DIR` env var overrides — tests point it at a temp dir) as one JSON file per key (hashed filename, atomic temp-file + rename, best-effort — a failed write only costs persistence) and restored at startup by `_load_persisted_cache`, which prunes entries past `_STALE_TTL` and drops corrupt/interrupted files — so `--reload` restarts don't start cold. Cache files are `.json`, which uvicorn's reload watcher (`*.py` only) ignores. Card-list endpoints are paginated: they take `?page=` and return an envelope `{data, page, pageSize, totalCount}` at 50 cards/page (`_PAGE_SIZE` — upstream latency scales with the requested page size, see "Behaviors worth knowing"). Card searches pass `select=` upstream (`_CARD_FIELDS`) so responses carry only the fields the frontend uses. `/sets/{id}` is answered from the cached sets list with no upstream call. Every card-list and card-detail response goes through `_with_price_changes`, which records a daily price snapshot, attaches a `priceChange` object to each priced card, and attaches `estimate` (`{value, date}` — the card's latest snapshot, which for TCGPlayer-priceless cards is the daily job's eBay sold-median) to cards with no market price (see `app/services/price_history.py`); this is wrapped in try/except so a DB hiccup never breaks the card proxy. Also serves `/cards/{id}/history` (`{points, variants}` — the headline daily series plus one series per TCGPlayer variant for multi-variant cards) and `/cards/{id}/ebay-price` (eBay estimate). Upstream calls use a (5s connect, 60s read) timeout. The sets list is **stale-while-revalidate at any age**: it sits on hot paths (smart search's set-name matching, the set-page completeness check), so an expired copy is served immediately while one background thread re-fetches — a request never blocks on the observed 50s upstream sets hangs; only a truly cold cache (first run ever) fetches synchronously and can 504. All routes sit behind the router-level `"api"` per-IP rate limit (120/min, shared with the portfolio router); `/cards/{id}/ebay-price` adds a stricter `ebay` scope (60/hour) because each uncached estimate is a live eBay scrape.
- `app/services/card_catalog.py` — the local card catalog over `card_catalog`: `upsert_cards` (insert-or-update from upstream card dicts, stripped to the frontend field set `_KEEP` — mirrors the router's `_CARD_FIELDS` — and stamped `price_updated_at`; a card whose stored row has a non-empty `tcgplayer.prices` keeps it when the incoming dict's block is empty — pokemontcg.io serves newest-set cards priceless for months, and neither the 6h background price refresh nor a proxy-fallback upsert may wipe the daily job's TCGCSV-filled prices, while the fresh `price_updated_at` still stops the refresh loop), `search` (paged `{data, page, pageSize, totalCount}` envelope plus the page's stale card ids; name = escaped ILIKE substring, number/set/rarity exact, type via the `|Fire|Flying|`-delimited `types` column), `get_card`/`card_payload` (payloads are copies so `priceChange` annotation never bleeds into the stored JSON), `set_count`, `price_is_stale` (`PRICE_TTL` 6h), and `is_synced`/`mark_full_sync` (the `catalog_meta` marker). List callers must gate on `is_synced`; single-row reads are always safe.
- `app/routers/auth.py` — register/login, JWT creation/validation (`get_current_user` dependency), password rules. Both routes are per-IP rate-limited (login 10 attempts/5 min — counted whether they succeed or fail, so a brute-forcer's lucky guess is blocked too; register 10/hour) via `app/services/rate_limit.py`.
- `app/services/rate_limit.py` — per-IP sliding-window rate limiting as a FastAPI dependency. `rate_limit(scope, times, seconds, what=...)` returns a dependency for a route or a router's `dependencies=[]`; same-name scopes share one budget (the cards and portfolio routers both register `"api"` at 120 req/min, so one client draws from a single allowance across both), and re-registering a scope with different numbers raises at import. Over-limit requests get a 429 with a `Retry-After` header and a "Too many … — try again in about Ns" detail; 429s pass back through CORSMiddleware, so browsers can read them. State is in-memory and per-process like the app's other caches (`reset()` clears it — conftest does this between tests; a multi-worker deploy multiplies every budget by the worker count). The client key is `request.client.host`; setting `RATE_LIMIT_TRUST_FORWARDED=1` keys on the first `X-Forwarded-For` hop instead — required behind a reverse proxy, dangerous without one (the header is client-controlled). Live scopes: `login` 10/5min, `register` 10/h, `api` 120/min, `ebay` 60/h.
- `app/routers/portfolio.py` — portfolio CRUD, batched price fetching, daily price snapshots, history endpoint. `fetch_prices` resolves all held cards in one upstream OR-query (`id:"a" OR id:"b" …`, chunks of 100) and caches per-card prices for 15 minutes (`_price_cache`); `/portfolio/add` seeds that cache from the card it already fetched. Each `/portfolio` row also carries a `price_change` (today vs the most recent prior snapshot, via `price_history.previous_prices`). Price/snapshot helpers now live in `app/services/price_history.py`. Routes sit behind the shared `"api"` per-IP rate limit (120/min, one budget with the cards router).
- `app/services/price_history.py` — the shared snapshot layer over `card_price_snapshot`: `extract_price` (variant preference order), `variant_prices` (every priced variant of a card, market→mid — the same rule per variant), `recorded_today` (card ids that already have a headline snapshot this UTC day — `record_snapshots` dedupes through it, and the snapshot job checks it before spending an eBay scrape), `record_snapshots` (≤1 row per card per variant per UTC day, `variant=""` — the headline series — by default; a same-day re-record refreshes that row's price to the latest value seen rather than freezing at the first read, so the day's point keeps step with the current market price), `record_variant_snapshots` (one row per named variant, only for cards with 2+ priced variants — a lone variant IS the headline, and duplicating it would double the table for most of the catalog), `previous_prices` (each card's most recent snapshot strictly before today), `latest_prices` (most recent snapshot, today included), `price_change`, `annotate_price_changes` (records today — headline and variants — + attaches `priceChange` to a list of card dicts, in place), `attach_estimates` (attaches `estimate` — the latest snapshot — plus a `priceChange` measured against the snapshot before that card's latest one, to cards with no TCGPlayer price, so tiles show the daily job's eBay median with the same daily-change chip as priced cards; `previous_prices` takes an optional `before` cutoff for exactly this), `card_history` (headline daily points for one card over a day window), and `card_variant_history` (the same, per named variant — `{}` for most cards). Every read helper filters to `variant == ""`; any new query against the snapshot table must do the same or variant rows pollute it (see `/portfolio/history`). Because the cards router annotates every browsed card, snapshots accumulate for anything users search or view — not just portfolio holdings.
- `scripts/snapshot_all.py` — standalone daily job that records a price snapshot for **every** card, so history is gap-free instead of only covering browsed/held cards. Pages the full card list (`GET /cards` with a `select=` of the full frontend field set, ~20k cards / ~82 pages of 250), extracts each price, and calls `record_snapshots` in chunks. Upstream flakes with transient 404s/timeouts, so each page is retried up to 3× with backoff; pages that still fail are remembered and **re-tried in a second pass at the end of the run** (after a 30s cool-down — flakes are usually transient, so this pass typically recovers them). A page failing both passes is **skipped, not fatal** — the crawl finishes the other ~80 and flags itself incomplete (missing cards get caught next run). Cards with **no TCGPlayer price** (~1.6k of the catalog: the newest sets plus old oddballs like e-Card holos) then get two fallbacks, in accuracy order. **First `tcgcsv_fill`** (`--no-tcgcsv` skips): real, variant-separated TCGplayer prices from the TCGCSV mirror via `app/services/tcgcsv.py`, one group fetch per set, **injected into the card dicts as a normal `tcgplayer.prices` block** and snapshotted — this runs BEFORE the catalog upsert (so the enriched dicts are what the catalog stores, and the app renders these cards as ordinarily TCGplayer-priced, variant tiles and all) and BEFORE the eBay pass (which only sees the remainder); unmatched sets are listed in the log (fix via `_GROUP_OVERRIDES`). After the TCGCSV fill, `record_variant_snapshots` runs over every crawled card (post-fill, so injected variant blocks get series too) — multi-variant cards get one extra snapshot row per variant per day. Then the catalog upsert: every crawled card into `card_catalog` (best-effort — a catalog failure never costs the day's snapshots), a complete, un-truncated run stamping the `last_full_sync` marker that lets the app's list endpoints trust the catalog (`--max-pages` smoke runs and crawls with dropped pages upsert but never stamp). **Then `ebay_fill`, the last resort**, over only the cards TCGCSV couldn't match: scrapes each card's eBay sold listings (via the `ebay_prices` fetch/parse/summarize pieces — `_estimate_one` distinguishes a failed fetch from a fetched-but-saleless page, which `estimate()` can't) and snapshots the sold **median** — newest sets first (`set.releaseDate` desc), skipping cards `recorded_today` says are already done (so a same-day re-run spends its budget on new ground), pausing `--ebay-pause` seconds between scrapes (default 5), capped at `--max-ebay` estimates per run (default 2000; `0` skips the pass). Saleless results are normal deep in the tail: they record nothing, stay gapped, and never stop the pass — only 5 **consecutive failed fetches** (the bot-block signature) end it early. **Then `recover_dropped`**, a final stage for **dropped pages** — pages pokemontcg.io couldn't serve even after the retry pass, whose cards `_collect` never saw so they're in none of `crawl.cards/prices/unpriced` and neither fill above could reach them (a distinct gap from cards it served priceless). It diffs the catalog against this run's crawled ids — any card the catalog holds that this run didn't crawl is, barring a rare upstream deletion, exactly a dropped page's card — presents those cards to the same `tcgcsv_fill` matcher (as a mini-crawl of unpriced candidates), snapshots the TCGCSV price, and re-upserts the recovered cards so their catalog price refreshes too. So a page outage doesn't punch a hole in the day's history — the price comes from the independent TCGCSV mirror instead. Gated to a full (non-`--max-pages`), already-synced run and skipped by `--no-tcgcsv`: without a synced catalog "uncrawled" doesn't mean "dropped", and a brand-new card the catalog has never seen still waits for the next complete crawl (no set/number to match on until then). The run finishes by calling `history_archive.compact` to move months older than the daily window into cold storage (`--no-compact` skips it; a compaction failure is logged and never fails the run — rows just stay in the DB until the next attempt). Idempotent (per-UTC-day dedupe; `record_snapshots` refreshes same-day rows in place, so a TCGCSV price recorded at 1pm replaces the morning's eBay median rather than duplicating it). No FastAPI app needed — it uses `app.database.SessionLocal` + its own upstream session. `--max-pages N` limits the crawl for smoke tests. A full run is slow (upstream latency, not payload); it keeps its own `_PAGE_SIZE = 250` deliberately — it's a retrying batch job where throughput beats per-request latency, unlike the user-facing 50/page in `app/routers/cards.py`. Scheduled by a launchd LaunchAgent (see "Daily snapshot job" below).
- `app/services/history_archive.py` — cold storage that keeps `card_price_snapshot` from growing ~1.1GB/year, structured like stock-market data: the DB holds daily rows for the recent window plus one "monthly close" per card+variant per older month; the full old dailies live on disk. `compact(db)` finds complete months that ended more than `DAILY_WINDOW_DAYS` (30) ago, exports each to one gzipped CSV (`.archive/price-history/YYYY-MM.csv.gz`, ~3–6MB/month, columns card_id/variant/snapshot_date/price; `PRICE_ARCHIVE_DIR` env overrides the dir, tests point it at a temp dir) via atomic tmp+rename, then deletes the month's rows **except each card+variant's last** (the close — kept per variant so variant charts get monthly closes too). Ordering is strict: the file must exist on disk before any row is deleted, an existing file is never rewritten, and re-compacting an already-thinned month is a silent no-op. `restore_month(db, "YYYY-MM")` loads a month's archived rows back, skipping ones already present (archives written before the variant column restore as headline rows). Run automatically at the end of the daily snapshot job; `scripts/archive_history.py` is the manual CLI (bare = compact now, `--list`, `--restore YYYY-MM`).
- `app/services/tcgcsv.py` — real TCGplayer prices from [TCGCSV](https://tcgcsv.com), a free nightly mirror of TCGplayer's catalog + price files (refreshed daily at 20:00 UTC), used by the snapshot job to price the cards pokemontcg.io returns with an empty `tcgplayer.prices` block (it lags on brand-new sets). `group_id_for_set(set_name, set_id)` matches a pokemontcg.io set to a TCGplayer "group" by normalized name (their names carry a `"ME05: "`-style code prefix that's stripped; `_GROUP_OVERRIDES`, keyed by pokemontcg.io set id, wins for stubborn mismatches — add entries as unmatched sets appear in the job log). `prices_for_group(group_id)` joins the group's products (card number from the `extendedData` `"Number"` entry; sealed products have none and are skipped — important, since a Booster Box carries real "Normal" prices) with its price rows, keyed by normalized number (`norm_number`: part before `/`, leading zeros stripped, case-folded — `"001/084"` → `"1"`, `"TG12/TG30"` → `"tg12"`), `subTypeName` mapped to the pokemontcg.io variant keys (`Normal`→`normal`, `Reverse Holofoil`→`reverseHolofoil`, …), rows with neither `marketPrice` nor `midPrice` dropped. `card_prices(set_id, set_name, number)` is the one-card convenience. Returned dicts are `tcgplayer.prices`-shaped, so `extract_price` and the frontend consume them unchanged. Groups list and per-group joins are memoized per process (the job is one process per day); failures aren't cached, so a later call can retry. Best-effort throughout — any fetch/parse failure returns empty/`None`, never raises. tcgcsv.com answers 401 to the default python-requests user agent — the module session sends an identifying `Mintly/1.0` UA (verified July 21, 2026). Batch-only by design: nothing on the request path calls it.
- `app/services/ebay_prices.py` — recent-eBay-sold price estimate for cards TCGPlayer can't price (since the TCGCSV fill, the daily job only sends it cards TCGCSV couldn't match; CardDetail's live estimate for a not-yet-crawled card is unchanged). `estimate(name, number, set_name)` builds a keyword query (`"<name> <number> -psa -bgs -cgc"`), fetches the completed-and-sold search page, parses it, and summarizes; results cached 12h (`_cache`). `_fetch_sold_html` seeds cookies from the eBay homepage then requests the search with a Referer, retrying once if it gets the bot-challenge page (`_looks_blocked`: the block page is a tiny "Error Page | eBay", a real page is ~1MB+). `parse_sold` walks `.su-card-container` tiles (BeautifulSoup + html.parser), reads the title from the image `alt`, the date from the "Sold <date>" caption, and the price *after* that caption (a leading price would be shipping/a range low), and drops graded/lots/proxies by title. `summarize` takes the most recent 25 sales, trims comps outside [0.35×, 3×] the median, and returns median/average/low/high/count/date-range/`source_url`/sample. Every failure path returns `count:0` — never raises.
- `app/models.py` — SQLAlchemy models.
- `app/database.py` — engine/session setup from `DATABASE_URL`.
- `tests/` — pytest suite for the auth, portfolio, card-search, price-history, eBay, TCGCSV, rate-limit, and card-catalog behavior plus the snapshot crawl's retry passes, TCGCSV fill, eBay fill, catalog upsert/sync marker, dropped-page recovery, and history archiving (181 tests, runs offline in ~15s). `conftest.py` sets `DATABASE_URL`/`SECRET_KEY`/`CARD_CACHE_DIR` env vars **before** importing app modules (they read config at import time), pins `RATE_LIMIT_TRUST_FORWARDED=0` (a dev `.env` may set `1`, which would flip `client_ip` for the whole suite), overrides `get_db` with an in-memory SQLite session, swaps `portfolio._session` for a `FakeUpstream`, and resets the rate limiter between tests (every TestClient request shares one client "IP", so the suite's cumulative logins would otherwise trip the login limit) — no Postgres or network needed. `test_search.py`/`test_history.py`/`test_catalog.py` likewise swap `cards.session` for a paged/priced fake (catalog tests seed rows + the sync marker through `card_catalog` itself); `test_ebay.py` monkeypatches `ebay_prices._fetch_sold_html` and parses fixture HTML; `test_tcgcsv.py` monkeypatches the `tcgcsv._fetch_*` helpers with fixture JSON (and resets the module memos between tests). Dev deps: `requirements-dev.txt`.
- Schema is managed by **Alembic** (`alembic/versions/`); `env.py` reads `DATABASE_URL` from `Backend/.env` and targets `app.models.Base.metadata`, so `alembic revision --autogenerate` works. The app no longer calls `create_all` at startup — after changing `app/models.py`, generate a migration, review it, and run `alembic upgrade head`. Databases created under the old `create_all` regime were stamped at the initial revision (`alembic stamp head` before the first real migration).

### Data model
- `users` — id, email, username, hashed_password (bcrypt), created_at, accepted_terms_at (when the user accepted the ToS at registration; NULL for accounts predating the requirement).
- `portfolio_cards` — one row per **purchase (lot)**: user_id, card_id (TCG API id like `base1-4`), card_name, quantity, purchase_price, purchase_date. The same card bought twice = two rows; the frontend groups them visually.
- `card_catalog` — one row per card, the local mirror of the upstream catalog the app browses from: card_id (PK), searchable columns (name, number, set_id, rarity, `|`-delimited types, release_date) extracted for querying, `data` (JSON — the card dict exactly as served to the frontend), and `price_updated_at` (when `data`'s tcgplayer block was last fetched; past 6h it's re-fetched in the background on view). Written by the daily crawl and by every proxy fallback.
- `catalog_meta` — key/value bookkeeping; the single `last_full_sync` row records when a complete crawl last finished, and its existence is what lets list endpoints serve from `card_catalog`.
- `card_price_snapshot` — one row per card per **variant** per UTC day: card_id, variant, price, snapshot_date. `variant` `""` is the **headline series** — the preferred-variant price `extract_price` picks, which every existing feature (daily change, estimates, portfolio history) reads; named variants (`"holofoil"`, `"reverseHolofoil"`, …) are recorded alongside it **only for cards with 2+ priced variants** (a single variant would just duplicate the headline), powering the per-variant chart lines and table changes. Shared across users, with a composite `(card_id, snapshot_date)` index. Written by the daily `scripts/snapshot_all.py` job (every TCGPlayer-priced card, then a TCGCSV fill for cards pokemontcg.io leaves unpriced, then a capped eBay-median fill for the remainder — the row doesn't record which source it came from), and also whenever any user loads their portfolio **or browses a priced card** through a card endpoint (all deduped per UTC day). It is the app-wide price-history store; portfolio value-over-time is derived from it by filtering to a user's holdings (`/portfolio/history`) — headline rows only, so there is no separate portfolio-snapshot table. Retention is tiered like stock-market data: the table holds daily rows for roughly the last 30–60 days plus one monthly-close row per card+variant per older month (~36MB/year before variants); the complete old dailies are offloaded — not deleted — to gzipped CSVs by `app/services/history_archive.py`. (Renamed from `portfolio_snapshot` — migration `b7e1c4d9f2a3`; `variant` added by `d4f8a21c7e56`, backfilling every pre-existing row as headline via the `''` server default.)
- All `DateTime` columns store **naive UTC**, set via the shared `utcnow()` helper in `app/models.py`; anything compared against them (e.g. the snapshot dedupe in `app/routers/portfolio.py`) must use `utcnow()` too, never local time. They serialize without a zone suffix, so the frontend must anchor them with `Z` before parsing (`parseUTCDate` in `Portfolio.tsx`) — a bare `new Date(...)` reads them as local time and shows evening purchases dated tomorrow.

### API endpoints
All card and portfolio endpoints share a per-IP budget of 120 requests/min; over-limit requests get a 429 with a `Retry-After` header (see `app/services/rate_limit.py` for all scopes).

| Endpoint | Notes |
|---|---|
| `POST /auth/register` | JSON body (never query params — passwords would hit logs). Password rules: ≥8 chars, ≥1 letter, ≥1 number. Requires `accepted_terms: true` (400 "You must agree to the Terms of Service" otherwise — message mirrored by the register form's checkbox); acceptance time stored on the user. Rate limited: 10/hour per IP. |
| `POST /auth/login` | OAuth2 form body; accepts email **or** username. Returns a 7-day JWT. Rate limited: 10 attempts per 5 min per IP, successes included. |
| `GET /search?q=&page=` | Smart search — see below. Returns `{data, page, pageSize, totalCount}` (50/page); priced cards carry a `priceChange`, priceless ones an `estimate` (latest snapshot — the daily job's eBay sold-median) when one exists. Served from the local catalog once synced (newest sets first); upstream fallback on zero results. |
| `GET /cards?name=&set_id=&number=&rarity=&type=&page=` | Filtered search; drives the frontend filter bar. Same paged envelope, same `priceChange`, same catalog-first serving. |
| `GET /cards/{card_id}` | Single card; drives the detail page. Catalog-first; carries `refreshing: true` while a >6h-old stored price is re-fetched in the background (CardDetail re-polls until it clears). Proxy fallback for unknown cards (cached 6h fresh, then stale-while-revalidate). Carries `priceChange` when a prior snapshot exists. |
| `GET /cards/{card_id}/history?days=` | `{points, variants}` from Mintly's snapshots: `points` is the headline daily series `[{date, price}]`; `variants` maps each TCGPlayer variant to its own series (populated only for cards with 2+ priced variants — `{}` otherwise). `days` defaults to 1825 (~5 years), clamped 1–3650. |
| `GET /cards/{card_id}/ebay-price` | Recent-eBay-sold estimate `{count, median, average, low, high, currency, since, until, source_url, sample}`. `count:0` when nothing usable. Best-effort scrape (12h cache). A usable estimate for a TCGPlayer-priceless card also refreshes today's price snapshot to that median (best-effort; never for a card TCGPlayer can price), so the card's history point matches the estimate shown. Extra rate limit: 60/hour per IP. |
| `GET /sets`, `GET /sets/{id}`, `GET /sets/{id}/cards?page=` | Sets list is cached; single sets served from it; drives filter dropdown + default view. Set-cards served from the catalog only when it holds the whole set (count ≥ the sets list's `total`), else proxied + upserted. Responses carry `priceChange` too. |
| `GET /portfolio` | Auth. Returns one row per lot with live price, P&L, daily `price_change`, and the card's real `image_url` (all fetched in one batched upstream call, 15-min cache). Also records today's snapshots as a side effect. |
| `GET /portfolio/history` | Auth. `[{date, total_value}]` from snapshots × current holdings; missing days carry the last known price forward. |
| `POST /portfolio/add` | Auth. `purchase_price` optional → falls back to current market price (400 if the card has none). |
| `PATCH /portfolio/{id}` | Auth. Update `purchase_price` and/or `quantity` on one lot. |
| `DELETE /portfolio/{id}` | Auth. Remove one lot. |

### Smart search (`/search`)
Lowercases and tokenizes the query (upstream matching is case-insensitive, so "Charizard" and "charizard" must build the same query string and share one cache entry — `/cards` likewise lowercases `name`/`set_id`, but `rarity`/`type` stay exact: era-specific dropdown strings), then:
1. Digits → card number; letters+digits (e.g. `swsh11`) → set id; rest → name words.
2. Scans name words for a real **set name** (longest contiguous match against the cached sets list) — "pikachu lost origin" → `name:"pikachu" set.id:swsh11`.
3. Name is always quoted (unquoted multi-word queries are a syntax error upstream → HTTP 400).
4. If nothing matches, retries dropping words from the front, then the back — "sleepy pikachu" falls back to "pikachu". "Nothing matches" means `totalCount == 0`, not an empty page — so requesting a page past the end of a valid query doesn't trigger the fallback.

The parse is shared by both execution paths: once the catalog is synced, the whole flow — including the word-drop fallback — runs as local DB queries (name filters become case-insensitive substring matches, so quoting gotchas can't reach upstream); only a catalog answer that is empty after every fallback retries the original query upstream (cached), and those results are upserted into the catalog.

## Daily snapshot job

`scripts/snapshot_all.py` records a price snapshot for every card so history is gap-free, and refreshes the `card_catalog` table the app browses from (TCGPlayer prices → TCGCSV fill for the unpriced → catalog upsert → eBay-median fill for whatever TCGCSV couldn't match — the eBay pass at the default 5s `--ebay-pause` is polite scraping whose length depends on how many cards TCGCSV leaves over — then compacts months older than 30 days into `Backend/.archive/price-history/`). On this dev Mac it runs daily at **1:00pm local** via a launchd LaunchAgent (`~/Library/LaunchAgents/com.mintly.daily-snapshot.plist`) — 13:00 PDT = 20:00 UTC / 13:00 PST = 21:00 UTC, i.e. on/just after TCGCSV's daily 20:00 UTC refresh, so the fill reads same-day prices (the crawl's 30–90 min of pokemontcg.io paging runs before the first TCGCSV fetch, adding propagation buffer). Output goes to `~/Library/Logs/mintly-daily-snapshot.log`. It needs the Postgres in `DATABASE_URL` running; if the Mac is asleep at 1pm, launchd runs it on the next wake.

**macOS TCC / Full Disk Access (required).** The repo lives under `~/Documents`, which macOS protects — a launchd job can't read files there by default, so a scheduled run fails immediately with `Operation not permitted`. The plist therefore invokes the **framework Python directly** (`/Library/Frameworks/Python.framework/Versions/3.14/bin/python3.14`, which is outside `~/Documents` so launchd can exec it), with `PYTHONPATH` pointing at the repo venv's `site-packages` and `WorkingDirectory` set to `Backend/` (so `.env` loads; the script itself puts `Backend/` on `sys.path` to import the `app` package). That python binary must be granted **Full Disk Access** so it can read the project:
1. System Settings → Privacy & Security → Full Disk Access → **+**
2. In the file dialog press **⌘⇧G**, paste `/Library/Frameworks/Python.framework/Versions/3.14/bin/python3.14`, add it, and toggle it **on**.
3. `launchctl kickstart gui/$(id -u)/com.mintly.daily-snapshot` and confirm the log shows `page 1/82 …` instead of the permission error.

(Alternative to granting FDA: move the repo out of `~/Documents`, e.g. to `~/GitHub`, and repoint the plist — then no special permission is needed.)

Managing it:
```bash
launchctl load   ~/Library/LaunchAgents/com.mintly.daily-snapshot.plist   # enable
launchctl unload ~/Library/LaunchAgents/com.mintly.daily-snapshot.plist   # disable
launchctl kickstart gui/$(id -u)/com.mintly.daily-snapshot                # run now
launchctl kill  TERM gui/$(id -u)/com.mintly.daily-snapshot               # stop a run
launchctl list | grep mintly                                             # status (col 1 = PID if running, col 2 = last exit)
tail -f ~/Library/Logs/mintly-daily-snapshot.log                         # watch output
```
The plist is machine-specific (absolute paths) and lives outside the repo; the job script is in `Backend/scripts/`. To change the time, edit `StartCalendarInterval` in the plist and `unload`/`load` it. To run it by hand from a terminal (which already has Documents access), just `cd Backend && venv/bin/python scripts/snapshot_all.py`.

## Behaviors worth knowing

- **Browsing is served from the local card catalog**: once the daily crawl has completed once (the `last_full_sync` marker), search/filter/set/detail requests read `card_catalog` in milliseconds instead of waiting on the upstream API, and keep working through upstream outages. Prices shown while browsing are at most ~6h old — a viewed card or list page with an older stored price is served instantly while a background thread re-fetches it (detail responses carry `refreshing: true`, which CardDetail re-polls on until the fresh number lands; list pages just serve fresher data to the next request). The portfolio's live 15-minute batched price fetch is unchanged — P&L stays fresher than the catalog. Brand-new sets reach users through the proxy fallback (upserted as they're browsed) until a crawl completes them; catalog results order newest-sets-first with name matching as case-insensitive substrings.
- **Price picking**: first available `market` (falling back to `mid` when the variant has no market value) among holofoil → normal → reverseHolofoil → 1stEditionHolofoil (`extract_price` backend, `getCardPrice` frontend — keep in sync). Snapshots recorded before July 15, 2026 used `mid`, so long price-history series have a small step at the switchover.
- **History chart**: computed against *current* holdings, so editing a quantity retroactively changes past points. Snapshots only record on days someone loads their portfolio. With <2 days of data the chart shows a flat placeholder line at today's value. Snapshot days are UTC, so a late-evening US visit records under the next calendar day's UTC date — the chart's newest point can read one day ahead of local; dedupe and chart bucketing use the same UTC day, so points stay one-per-day.
- **Newest sets can lack TCGPlayer prices upstream — TCGCSV fills them**: the pokemontcg.io API lags on 2026 "Mega Evolution" era sets (was 0/N for me4, me3, me2pt5; it backfills over time — `me1` is now fully priced upstream). The daily job closes that gap with real, variant-separated TCGplayer prices from the TCGCSV mirror, injected into the catalog rows — so after one run those cards browse, chart, and add exactly like ordinarily-priced cards (variant tiles included), instead of showing a noisy eBay median (eBay can't separate variants and has a price floor that made a 4¢ common show as ~$4). The "prices unavailable" UI note and blank-price add rejection still exist for cards no source can price; a card browsed before the crawl has enriched it still uses the live eBay fallback. Source priority: pokemontcg.io's own TCGplayer figure → TCGCSV → eBay.
- **eBay fallback for priceless cards (last resort, after TCGCSV)**: `/cards/{id}/ebay-price` estimates a value from recent *sold* eBay listings for cards TCGPlayer can't price. CardDetail shows it and pre-fills the add form with the median, so those cards are still addable. The estimate is the median/average of the most recent ~25 ungraded single-card sales, with graded slabs/lots/proxies excluded by title and far-off outliers trimmed around the median. eBay markup and bot checks change, so treat `count:0` as normal, not an error. Verified live (e.g. Mega Lucario ex 188 → ~$250 median from ~20 recent sales). The daily snapshot job records the same estimator's **median as the card's history snapshot** only for priceless cards its TCGCSV fill couldn't match (capped per run, newest sets first) — so their charts and `DayChange` chips work too, and **search/set tiles show that stored median** styled like a normal price with a muted "eBay est." label and the usual daily-change chip (`attach_estimates` on every card response — reading snapshots, never live-scraping on browse; the chip appears once a card has two snapshot days, same rule as priced cards). On the card detail page the live `/cards/{id}/ebay-price` scrape *does* refresh today's snapshot to the freshly-scraped median (guarded to priceless cards), and CardDetail overlays that same median onto the chart's newest point — so an eBay card's graph and its stored history both stay in step with the estimate shown above the chart, mirroring how `record_snapshots` keeps a TCGPlayer card's day point current. A card's history can therefore mix sources: eBay medians while TCGPlayer is blank, switching to TCGPlayer market once upstream backfills (like `me1` did) — expect a step at the switchover, same as the July 15, 2026 mid→market one.
- **Daily price change**: any priced card browsed through a card endpoint gets a snapshot, and responses carry `priceChange` (today vs the most recent prior-day snapshot: `{amount, percent, since}`). `/portfolio` rows carry the same as `price_change`. The frontend renders it as a `DayChange` chip next to the price — so a card's daily move is visible without opening or adding it. It's absent until at least one prior-day snapshot exists for that card.
- **Per-card price history**: `/cards/{id}/history` returns Mintly's own daily snapshots (there is no upstream history endpoint). The daily `scripts/snapshot_all.py` job records a point for every TCGPlayer-priced card each day (every priceless card is attempted via the eBay fill too, but only those with ≥3 recent ungraded sales actually record a point — the rest stay gapped), so charts fill in one day at a time for the whole catalog going forward — but depth is still bounded by how long the job has been running (snapshots start July 14, 2026), so charts are short until it accumulates. The default window is ~5 years; the chart shows a "not enough history yet" note with fewer than two points. **Resolution is tiered, stock-chart style**: daily points for roughly the last 30–60 days, then one point per month (each card's month-end close, thanks to `history_archive` compaction) — so the 1M range stays daily while 6M/1Y/All go monthly as data ages. Recharts just connects the sparser points; nothing in the frontend knows about the tiers. `/portfolio/history`'s carry-forward likewise rides monthly closes for old dates.
- **Per-variant price history**: cards with 2+ priced TCGPlayer variants get one snapshot per *variant* per day alongside the headline row (recorded by the daily job and on browse), served as the `variants` map in `/cards/{id}/history`. CardDetail's chart renders them as one colored line per variant (fixed color per variant name, legend + line-end labels) and the variants table adds a per-variant daily-change chip. Variant rows only started accumulating July 21, 2026, so on day one a non-preferred variant shows as a single dot; the preferred variant's line carries the full pre-variant history (the headline series *was* that variant — `mergeHeadline` in `variants.ts` splices it in client-side). Single-variant cards record no variant rows (their one variant is the headline) and keep the original area chart.
- **Add button** shows "Adding…" and blocks double-clicks (the add round-trips to the external API, 1–3s).
- **Structured data is client-rendered and honesty-first**: all JSON-LD is injected by React (Googlebot executes JS, so it sees it; verified live — a card page serves the site `@graph` plus a `Product` block with name/image/description/sku/brand and no `offers`). Markup only ever describes what's visible on the page: the per-card `Product` block carries no `offers` at all (Mintly is a tracker, not a store — the market/estimate prices shown are third-party figures, not Mintly listings), and descriptions mirror the on-page copy — Google treats markup for hidden/misleading content as spam. Non-JS crawlers see only the static `index.html` title/description; prerendering or SSR would be needed for them (see next steps).
- **Rate limits are sized for humans, walls for scripts**: a browsing user never sees them (debounced search + pagination stays far under 120/min), but a scraper burning the upstream API quota, a credential-stuffing loop, or an eBay-estimate hammer hits a 429 fast. Login attempts count toward the limit whether they succeed or fail — after 10 in 5 minutes even the correct password gets a 429, which is the point (a brute-forcer's lucky guess is blocked too). The login form surfaces the 429's "try again in about Ns" detail instead of "Invalid credentials" (`login()` in `api.ts`), so a locked-out user isn't sent hunting for a typo. Budgets are per-process and reset on restart, same as the other in-memory caches.
- **Session expiry**: JWTs last 7 days. Any authed call after expiry gets a 401 → token cleared → redirect to `/login` with a "session expired" notice (`SessionExpiredError` in `api.ts`, redirect via `useSessionRedirect` in `hooks.ts`).
- **Upstream latency scales with the requested `pageSize`, not the payload**: benchmarked (July 16, 2026) `pageSize=250` at 20–60s with dropped connections vs `pageSize=50` at 2–5s — for near-identical payload sizes (~35–40KB). Hence `_PAGE_SIZE = 50` in `app/routers/cards.py`; don't raise it without re-measuring. This now only applies to the proxy fallback path — a search that misses the catalog (unsynced DB, zero-result query, brand-new set) costs a few seconds (measured 2.8s cold, ~8ms warm); expired cache entries never block — they're served stale while a background thread refreshes (up to 24h, then synchronous again) — and the cache survives restarts via its disk mirror, so only genuinely never-fetched queries pay the cold cost. Portfolio loads are one batched call regardless of collection size (measured ~0.8s cold, ~4ms warm for 5 cards).
- **Upstream is occasionally flaky, not just slow**: observed (July 10, 2026) `GET /sets` transiently returning 404 and taking ~50s when it did succeed. All upstream calls now carry a (5s connect, 60s read) timeout so a hung connection can't pin a worker, and the sets list is served stale at **any** age while a background thread refreshes — no request ever waits out a sets re-fetch, and `/search`/set pages keep working through flakes as long as the sets list has been fetched once ever (it persists to disk across restarts). A flake on a genuinely cold cache (first run ever) still surfaces as `{"detail": "Failed to fetch sets"}`; there is no retry, only the next request trying again. `fetch_prices` skips failed/timed-out chunks, so `/portfolio` degrades to missing prices instead of erroring. Once the catalog is synced, browsing doesn't touch upstream at all — flakes only affect the fallback paths and background price refreshes (which just leave rows stale for the next attempt).
- **Historic merged rows**: before lots existed, duplicate adds were averaged into one row. Those can't be un-averaged; new purchases keep exact prices.
- **Card image URLs can't be guessed from card ids**: newer sets (Mega Evolution era) are hosted on `images.scrydex.com`, and `images.pokemontcg.io` answers unknown paths with a 404 whose body is a *card-back PNG* that browsers render anyway (no `onerror`). `/portfolio` therefore returns each row's real `image_url` (fetched alongside prices, same cache); the frontend's `getCardImageUrl` guess is only a fallback. All card artwork renders through the shared `CardImage` component, which reserves the 5:7 card ratio (so the grid never shifts as images load) and degrades a genuinely-failed or missing image to a muted card-shaped placeholder instead of a blank gap or broken-image icon (the card-back-PNG case still renders as an image — it's a valid 200 response, not a load error).
- **Rarity names are era-specific** exact strings (old: "Rare Holo"; Scarlet & Violet: "Double Rare") — a rarity filter + wrong-era set legitimately returns nothing.

## Suggested next steps

1. **Deployment prep** — API base URL (`VITE_API_BASE`) and CORS origins (`CORS_ORIGINS`) are env-configurable now; card browsing is now backed by Postgres (`card_catalog` is shared state, so N workers serve identical catalog answers); remaining concern: the leftover in-memory state is single-process (the portfolio price cache, `ebay_prices._cache`, the `ebay_prices._session` cookie jar, and the rate limiter's counters — N workers means N× every rate budget; the proxy-fallback response cache has a disk mirror, but it's only read at startup — workers still cache independently in memory). Multiple workers each scrape/cache independently. A deploy behind a reverse proxy also needs `RATE_LIMIT_TRUST_FORWARDED=1` or every client shares the proxy's IP budget. The price-history archive (`Backend/.archive/price-history/`) is also host-local disk — a deployed snapshot job needs that directory on durable storage (or `PRICE_ARCHIVE_DIR` pointed somewhere durable), and it should be included in backups since the DB alone no longer holds full history.
2. **Scheduled snapshots** — done on this dev Mac via a launchd LaunchAgent running `scripts/snapshot_all.py` daily (see "Daily snapshot job"). For a deployed environment, replace the LaunchAgent with a server-side cron / systemd timer / cloud scheduler running the same script against the production DB (a Claude cloud routine can't reach a local Postgres).
3. **Frontend tests** — the backend routers are covered (`Backend/tests/`, 181 tests); the React pages are not.
4. **Store quantities in snapshots** if "value as held at the time" ever matters for the chart.
5. **eBay scraping robustness** — the estimate depends on eBay's `.su-card-container` markup and unauthenticated access. The TCGCSV fill has shrunk its role to a true last resort (old oddballs TCGCSV doesn't cover, plus CardDetail's live estimate for not-yet-crawled cards), but that tail still relies on it; consider eBay's official Browse/Marketplace API or a headless fallback if the scrape starts getting blocked or the layout changes.
6. **SEO beyond structured data** — JSON-LD, titles, and the meta description exist (see "Structured data" behavior above), but the app is client-rendered: non-JS crawlers see only the `index.html` shell. When deployed, add a `robots.txt` + sitemap (needs the real domain) and consider prerendering/SSR for card pages if search traffic matters.

## Gotchas for developers

- Run `npm`/`eslint` commands from `Frontend/mintly/`, not the repo root.
- A fresh database proxies all browsing upstream until `scripts/snapshot_all.py` completes once and stamps the sync marker — slow searches on a new environment mean the catalog isn't populated yet, not a regression. Truncated (`--max-pages`) or partially failed crawls upsert cards but deliberately never stamp it.
- The eslint react-hooks rules are strict (v7): no synchronous `setState` inside `useEffect` — defer via promise callbacks or timeouts (see `Search.tsx`/`CardDetail.tsx`), or remount the component with a `key` so its state re-initializes instead of being reset in the effect (see `PriceHistoryChart`).
- Every backend file save restarts the dev server; the card/search response cache is restored from its disk mirror, but the portfolio price cache is memory-only → the first portfolio load after a restart is slow.
- CSS Modules typos fail silently: a mis-keyed `styles.foo` resolves to `undefined`, so the element renders with no class and no error (TS types module classes as `string`, so it can't catch a wrong key). After any styling change, check the page in the browser, not just `npm run build`. Only genuinely shared classes remain as plain strings in JSX and must exist in `App.css`; everything else goes through a module's `styles` object.
- Card searches only return the fields listed in `_CARD_FIELDS` (`app/routers/cards.py`). If the frontend `Card` type grows a field, add it there too or it will arrive undefined. (`priceChange` is added server-side in `_with_price_changes`, not selected upstream.)
- eBay scraping (`app/services/ebay_prices.py`) needs a two-step request (homepage for cookies, then the search with a Referer) — a bare request gets a tiny "Error Page | eBay". When changing `parse_sold`, verify against a freshly fetched sold-listings page: `.su-card-container` tiles, title in the image `alt`, and the price *after* the "Sold <date>" caption.
- `Backend/.env` holds real secrets and is gitignored — never commit it or move its values into query strings/logs.
