# Mintly — Handoff Document

*Last updated: July 24, 2026*

A Pokemon TCG portfolio tracker: search cards, view live market prices, and track a collection's value over time. Live in production at **https://mintlytcg.com** (see "Production deployment").

## Stack

| Layer | Tech |
|---|---|
| Backend | FastAPI, PostgreSQL, SQLAlchemy, JWT auth (python-jose + passlib/bcrypt) |
| Frontend | React 19, TypeScript, Vite, React Router 7, Recharts |
| Data source | [Pokemon TCG API](https://pokemontcg.io) (prices via TCGPlayer); [TCGCSV](https://tcgcsv.com) fills TCGplayer prices for cards it lacks; eBay sold listings as last resort |

## Running locally

**Backend** (from `Backend/`):
```bash
source venv/bin/activate
alembic upgrade head                 # apply DB migrations (needed on first run / after pulling schema changes)
uvicorn app.main:app --reload        # http://localhost:8000, docs at /docs
pip install -r requirements-dev.txt  # test deps (pytest, httpx)
pytest tests/ -q                     # backend tests — offline (in-memory SQLite + fake upstream API)
```
Requires a `.env` in `Backend/` (not committed):
```
DATABASE_URL=postgresql://username@localhost:5432/mintly
SECRET_KEY=...
POKEMON_TCG_API_KEY=...
CORS_ORIGINS=http://localhost:5173   # optional — comma-separated allowed frontend origins (this is the default)
RATE_LIMIT_TRUST_FORWARDED=1         # optional — ONLY behind a reverse proxy: keys rate limits on X-Forwarded-For
FRONTEND_BASE_URL=http://localhost:5173  # optional — where password-reset links point (this is the default)
SMTP_HOST=smtp.resend.com            # optional — unset = reset emails print to the server console instead of sending (the right dev mode)
SMTP_PORT=587                        # optional — 587 STARTTLS (default) or 465 implicit TLS
SMTP_USER=resend                     # optional — SMTP login (Resend's is the literal string "resend")
SMTP_PASSWORD=...                    # optional — the password / provider API key
MAIL_FROM="Mintly <noreply@mintlytcg.com>"  # optional — From address, display-name form allowed (quote it: spaces); defaults to SMTP_USER
EBAY_EPN_CAMPAIGN_ID=...             # optional — eBay Partner Network campaign id: tags every eBay source_url with EPN affiliate params (unset = plain links)
ADMIN_EMAILS=you@example.com         # optional — comma-separated account emails granted the /admin dashboard (unset = no admins; list only addresses belonging to your own registered account)
```

**Frontend** (from `Frontend/mintly/`):
```bash
npm install
npm run dev                          # http://localhost:5173
npm run build                        # type-check + production build
npx eslint src/                      # lint (strict react-hooks rules enabled)
```
The API base URL comes from `VITE_API_BASE` (see `.env.example`; baked in at build time). Unset it for local dev — it defaults to `http://localhost:8000`. `VITE_TCGPLAYER_IMPACT_LINK` (optional, commented in both env files) is the Impact tracking-link base for the TCGplayer affiliate program — unset, CardDetail's Buy buttons render plain untracked TCGplayer links. `VITE_EBAY_EPN_CAMPAIGN_ID` (optional, commented in both env files) is the eBay Partner Network campaign id — the same value as the backend's `EBAY_EPN_CAMPAIGN_ID`; it tags CardDetail's "Search on eBay" button with EPN affiliate params (unset = plain eBay links).

## Architecture

### Backend files
- `app/main.py` — app assembly, and the uvicorn target (`app.main:app`): creates the FastAPI app, configures CORS (origins from `CORS_ORIGINS` env var, comma-separated; defaults to `http://localhost:5173`), and includes the auth/portfolio/cards/health/sitemap/admin routers.
- `app/routers/health.py` — `GET /health`, the probe an uptime monitor should ping: runs `SELECT 1` through the request's DB session and answers `{"status": "ok"}`, or 503 `database unavailable` when the query fails — so a live process in front of a dead Postgres still trips the monitor (pinging the site root would only prove the static frontend serves). Unauthenticated and deliberately outside every rate-limit scope: a monitor polling every 5 minutes must never see a 429, and the probe costs one trivial query.
- `app/routers/sitemap.py` — `GET /sitemap.xml`, the crawler-facing URL list: the public static pages (`/`, `/search`, `/terms`, `/privacy` — authed pages are deliberately absent, crawlers only see their login prompt) plus one `/card/{id}` entry per `card_catalog` row (ordered by card id), each URL built on `FRONTEND_BASE_URL` (the same env var reset links use, so one setting names the site everywhere). Catalog reads are wrapped best-effort — a DB hiccup still serves the static pages, never a 500. Registered under the shared `"api"` rate-limit scope (120/min, one budget with the cards/portfolio routers). `Frontend/mintly/public/robots.txt` (copied into `dist/` by Vite) allows all crawling and points at `https://mintlytcg.com/sitemap.xml`; the Caddyfile routes `/sitemap.xml` to the api container so the sitemap serves from the site root, where that reference expects it.
- `app/routers/admin.py` — `GET /admin/stats`, the admin dashboard's numbers: read-only aggregate queries over the app's own tables (no upstream calls, nothing mutated). Users (total, new 7d/30d, with a portfolio), signups per UTC day over the last 30 days (zero-filled, for the dashboard's bar chart), the 10 most recent signups with per-user lot counts, portfolio totals (lots, distinct cards, summed quantity), catalog health (row count, stale-price count vs `card_catalog.PRICE_TTL`, the `last_full_sync` value), snapshot health (total rows, headline rows today, newest snapshot), and `pg_database_size` (best-effort — `null` on SQLite/tests, wrapped in rollback so a failure can't poison the session). Gated by `get_admin_user`: a valid JWT whose account `app/services/admin_access.py` doesn't recognize gets a plain **404, not 403** — probing the URL reveals nothing; keep it that way. Registered under the shared `"api"` rate-limit scope.
- `app/services/admin_access.py` — who counts as an admin: the `ADMIN_EMAILS` env var (comma-separated account emails, case-insensitive, read at import like the mailer's config; tests monkeypatch the parsed `_ADMIN_EMAILS` set). Unset — the default — means no admins, so the feature is invisible until configured. Admin is configuration, not schema: no column, no migration; list only addresses that already belong to your own registered account (registration doesn't verify email ownership, so a listed-but-unregistered address could be claimed by anyone). `is_admin(user)` is also read by `user_info` in auth.py, which is how `/auth/me` carries the `is_admin` flag the frontend keys the Profile→Admin link on.
- `app/routers/cards.py` — card/set endpoints + smart search, served **catalog-first**: once a complete crawl has stamped the sync marker (`catalog_meta.last_full_sync` — checked per request via `card_catalog.is_synced`), `/search`, `/cards`, and `/sets/{set_id}/cards` are answered straight from the `card_catalog` table (single-digit ms, no upstream call), and `/cards/{card_id}` always prefers a catalog row when one exists. Catalog answers order newest-sets-first (release date desc, then natural card-number order) and match names as case-insensitive substrings. The upstream proxy below remains the fallback for: an unsynced catalog (fresh DB), zero-result queries (typos, or sets newer than the last crawl), unknown single cards, and sets the catalog holds incompletely (`set_count` < the sets list's `total` — a half-crawled set must never serve confidently-short pages); fallback results are upserted back into the catalog (`_upsert_results`, best-effort), so new sets converge before the next crawl. **Stale prices refresh in the background**: a catalog row whose `price_updated_at` is past `card_catalog.PRICE_TTL` (6h) is served instantly anyway — `/cards/{card_id}` adds `refreshing: true` (the frontend re-polls on it) and list pages batch their stale ids — while `_refresh_prices_in_background` re-fetches via one `id:"…" OR …` upstream call (`refresh_card_prices` is the synchronous, testable core; per-id-set dedupe through `_refreshing`; a failed refresh just leaves the row stale for the next view). All catalog access is wrapped best-effort: a DB hiccup drops to the proxy, never a 500. The proxy path keeps its response cache (covers searches, single-card lookups, and the sets list, keyed per query+page). Cache entries are **stale-while-revalidate**: fresh for 6h (`_CACHE_TTL`), then served immediately while one daemon thread per key re-fetches in the background (`_refresh_in_background`; a failed refresh leaves the stale entry for the next attempt); past 24h (`_STALE_TTL`) the entry is dead and the fetch is synchronous again. Every cache write is also **mirrored to disk** (`Backend/.cache/cards`, gitignored; `CARD_CACHE_DIR` env var overrides — tests point it at a temp dir) as one JSON file per key (hashed filename, atomic temp-file + rename, best-effort — a failed write only costs persistence) and restored at startup by `_load_persisted_cache`, which prunes entries past `_STALE_TTL` and drops corrupt/interrupted files — so `--reload` restarts don't start cold. Cache files are `.json`, which uvicorn's reload watcher (`*.py` only) ignores. Card-list endpoints are paginated: they take `?page=` and return an envelope `{data, page, pageSize, totalCount}` at 50 cards/page (`_PAGE_SIZE` — upstream latency scales with the requested page size, see "Behaviors worth knowing"). Card searches pass `select=` upstream (`_CARD_FIELDS`) so responses carry only the fields the frontend uses. `/sets/{id}` is answered from the cached sets list with no upstream call. Every card-list and card-detail response goes through `_with_price_changes`, which records a daily price snapshot, attaches a `priceChange` object to each priced card, and attaches `estimate` (`{value, date}` — the card's latest snapshot, which for TCGPlayer-priceless cards is the daily job's eBay sold-median) to cards with no market price (see `app/services/price_history.py`); this is wrapped in try/except so a DB hiccup never breaks the card proxy. Also serves `/cards/{id}/history` (`{points, variants}` — the headline daily series plus one series per TCGPlayer variant for multi-variant cards) and `/cards/{id}/ebay-price` (eBay estimate). Upstream calls use a (5s connect, 60s read) timeout. The sets list is **stale-while-revalidate at any age**: it sits on hot paths (smart search's set-name matching, the set-page completeness check), so an expired copy is served immediately while one background thread re-fetches — a request never blocks on the observed 50s upstream sets hangs; only a truly cold cache (first run ever) fetches synchronously and can 504. All routes sit behind the router-level `"api"` per-IP rate limit (120/min, shared with the portfolio router); `/cards/{id}/ebay-price` adds a stricter `ebay` scope (60/hour) because each uncached estimate is a live eBay scrape.
- `app/services/card_catalog.py` — the local card catalog over `card_catalog`: `upsert_cards` (insert-or-update from upstream card dicts, stripped to the frontend field set `_KEEP` — mirrors the router's `_CARD_FIELDS` — and stamped `price_updated_at`; with `keep_stored_prices=True`, the request-path default, a stored non-empty `tcgplayer.prices` survives both an incoming EMPTY block — pokemontcg.io serves newest-set cards priceless for months, and the 6h background refresh / proxy-fallback upserts must not wipe the daily job's TCGCSV-filled prices — and, when the stored block is marked `tcgplayer.priceSource == "tcgcsv"`, an incoming upstream figure too, since that mark means the daily job judged upstream's price wrong for this card (the WHOLE stored block is kept either way — a job-injected `tcgplayer.url` product link rides along, so buy links survive refreshes); the fresh `price_updated_at` still stops the refresh loop either way. The daily crawl passes `keep_stored_prices=False`: it re-arbitrates every card's price source with fresh data, and its verdict lands verbatim — including clearing the stored block of a card no source prices any more, which would otherwise fossilize a retracted price forever. The flag also guards the `images` block the daily job arbitrates: a stored `images.source: "tcgplayer"` substitution — the job swapped dead upstream image URLs for the TCGplayer product scan — survives request-path refreshes (upstream still serves the dead URLs it replaced), and an unchanged upstream URL keeps its `images.verified` stamp so the next crawl doesn't HEAD-check it again; the crawl's authoritative upsert re-arbitrates both), `search` (paged `{data, page, pageSize, totalCount}` envelope plus the page's stale card ids; name = escaped ILIKE substring, number/set/rarity exact, type via the `|Fire|Flying|`-delimited `types` column), `get_card`/`get_cards` (single or batched primary-key fetch)/`card_payload` (payloads are copies so `priceChange` annotation never bleeds into the stored JSON), `set_count`, `price_is_stale` (`PRICE_TTL` 6h), and `is_synced`/`mark_full_sync` (the `catalog_meta` marker). List callers must gate on `is_synced`; single-row reads are always safe. The portfolio router reads `get_cards` too, to price cards pokemontcg.io returns unpriced.
- `app/routers/auth.py` — register/login, JWT creation/validation (`get_current_user` dependency), password rules. Both routes are per-IP rate-limited (login 10 attempts/5 min — counted whether they succeed or fail, so a brute-forcer's lucky guess is blocked too; register 10/hour) via `app/services/rate_limit.py`. A cluster of authed self-service account endpoints backs the Profile page: `GET /auth/me` returns the account fields (`user_info` — email, username, created_at, accepted_terms_at, plus the computed `is_admin` flag from `admin_access`; never the password hash); `PATCH /auth/me` updates email and/or username (only the fields sent are touched, each checked for uniqueness against *other* users so re-saving your own value is fine, email lightly format-validated by `valid_email`); `POST /auth/me/password` changes the password (verifies the current one with `pwd_context.verify`, then applies `password_error`'s rules to the new one — rate-limited 10/5 min under a `"password"` scope as cheap defense in depth if a token is ever stolen). `DELETE /auth/me` (authed) is self-service account deletion: it bulk-deletes the user's `portfolio_cards` and `password_reset_tokens` first (neither FK has an `ON DELETE` cascade, so Postgres would otherwise reject the parent delete), then the `User` row. The shared `card_price_snapshot` rows are per-card, not per-user, so they're intentionally left in place. **Password reset** (both unauthed): `POST /auth/forgot-password` takes `{email}` and always answers the same generic message whether or not the address has an account — only the inbox learns the difference (anti-enumeration; keep the responses identical). For a real account it mints a `secrets.token_urlsafe(32)` token, stores only its sha256 (`hash_token`) in `password_reset_tokens` with a 30-min expiry (`RESET_TOKEN_TTL_MINUTES`) — deleting any older tokens first, so one live link per account — and emails `FRONTEND_BASE_URL/reset-password?token=<raw>` via `app/services/mailer.py` (a send failure is logged and swallowed: the response must not change). Rate-limited 5/hour (`forgot` scope) since each valid hit sends an email. `POST /auth/reset-password` takes `{token, new_password}`: looks up the sha256, rejects missing/used/expired tokens with one uniform 400 ("This reset link is invalid or has expired — request a new one"), applies `password_error`'s rules (a weak password 400s *without* burning the token), then swaps the hash and stamps `used_at` (single-use). Shares the `password` 10/5min scope with the authed change-password route. Existing JWTs are not invalidated by a reset (they're stateless; same as an authed password change).
- `app/services/rate_limit.py` — per-IP sliding-window rate limiting as a FastAPI dependency. `rate_limit(scope, times, seconds, what=...)` returns a dependency for a route or a router's `dependencies=[]`; same-name scopes share one budget (the cards, portfolio, sitemap, and admin routers all register `"api"` at 120 req/min, so one client draws from a single allowance across them), and re-registering a scope with different numbers raises at import. Over-limit requests get a 429 with a `Retry-After` header and a "Too many … — try again in about Ns" detail; 429s pass back through CORSMiddleware, so browsers can read them. State is in-memory and per-process like the app's other caches (`reset()` clears it — conftest does this between tests; a multi-worker deploy multiplies every budget by the worker count). The client key is `request.client.host`; setting `RATE_LIMIT_TRUST_FORWARDED=1` keys on the first `X-Forwarded-For` hop instead — required behind a reverse proxy, dangerous without one (the header is client-controlled). Live scopes: `login` 10/5min, `register` 10/h, `password` 10/5min (change + reset share it), `forgot` 5/h, `api` 120/min, `ebay` 60/h.
- `app/routers/portfolio.py` — portfolio CRUD, batched price fetching, daily price snapshots, history endpoint. `fetch_prices` resolves all held cards in one upstream OR-query (`id:"a" OR id:"b" …`, chunks of 100) and caches per-card prices for 15 minutes (`_price_cache`); `/portfolio/add` seeds that cache from the card it already fetched. **Prices come from every source, freshest first** (`_fallback_prices`): the live pokemontcg.io TCGplayer figure, then — for cards it returns unpriced (the newest sets it lags on, e.g. Ascended Heroes) — the real TCGplayer price the daily job seeded into the local `card_catalog` from TCGCSV, then the latest recorded `card_price_snapshot` (the daily job's eBay sold-median). So the portfolio tracks the same value the browse pages show instead of a blank price; the fallback is used by both `/portfolio` (current price + image, P&L, daily change) and `/portfolio/add`'s auto-price when no purchase price is given. Upstream stays the source of truth wherever it has a price — the fallback only fills the gap — and the cache/add flow store the *resolved* price (not a bare upstream `None`), so a later load can't read back a cached `None` and hide the fallback. A card whose upstream chunk fails and that no fallback can price stays uncached, so a transient upstream error retries next load. Each `/portfolio` row also carries a `price_change` (today vs the card's daily-change baseline, via `price_history.change_baselines`). Price/snapshot helpers now live in `app/services/price_history.py`. Routes sit behind the shared `"api"` per-IP rate limit (120/min, one budget with the cards router).
- `app/services/price_history.py` — the shared snapshot layer over `card_price_snapshot`: `extract_price` (variant preference order), `variant_prices` (every priced variant of a card, market→mid — the same rule per variant), `recorded_today` (card ids that already have a headline snapshot this UTC day — `record_snapshots` dedupes through it, and the snapshot job checks it before spending an eBay scrape), `record_snapshots` (≤1 row per card per variant per UTC day, `variant=""` — the headline series — by default; a same-day re-record refreshes that row's price to the latest value seen rather than freezing at the first read, so the day's point keeps step with the current market price), `record_variant_snapshots` (one row per named variant, only for cards with 2+ priced variants — a lone variant IS the headline, and duplicating it would double the table for most of the catalog), `previous_prices` (each card's most recent snapshot strictly before today), `latest_prices` (most recent snapshot, today included), `price_change`, `change_baselines` (the comparison point for the daily-change chip: normally the most recent prior-day snapshot — but a day's row is refreshed in place to the last price seen, so right after the UTC rollover yesterday's close equals the current price and every chip would read $0.00 until the next crawl lands; when close == current the baseline steps one day further back, `since` carrying the older date, so the chip keeps showing the most recent real move), `annotate_price_changes` (records today — headline and variants — + attaches `priceChange` vs each card's `change_baselines` baseline to a list of card dicts, in place), `attach_estimates` (attaches `estimate` — the latest snapshot — plus a `priceChange` measured against the snapshot before that card's latest one, to cards with no TCGPlayer price, so tiles show the daily job's eBay median with the same daily-change chip as priced cards; `previous_prices` takes an optional `before` cutoff for exactly this), `card_history` (headline daily points for one card over a day window), and `card_variant_history` (the same, per named variant — `{}` for most cards). Every read helper filters to `variant == ""`; any new query against the snapshot table must do the same or variant rows pollute it (see `/portfolio/history`). Because the cards router annotates every browsed card, snapshots accumulate for anything users search or view — not just portfolio holdings.
- `scripts/snapshot_all.py` — standalone daily job that records a price snapshot for **every** card, so history is gap-free instead of only covering browsed/held cards. Pages the full card list (`GET /cards` with a `select=` of the full frontend field set, ~20k cards / ~82 pages of 250), extracts each price, and calls `record_snapshots` in chunks. Upstream flakes with transient 404s/timeouts, so each page is retried up to 3× with backoff; pages that still fail are remembered and **re-tried in up to 3 end-of-run sweeps** (cool-downs doubling 30s → 60s → 120s — a flake burst that outlives one pause rarely outlives three minutes). A page failing every sweep is **skipped, not fatal** — the crawl finishes the other ~80 and flags itself incomplete (missing cards get caught next run). Cards with **no TCGPlayer price** (~1.6k of the catalog: the newest sets plus old oddballs like e-Card holos) then get two fallbacks, in accuracy order. **First `tcgcsv_fill`** (`--no-tcgcsv` skips): real, variant-separated TCGplayer prices from the TCGCSV mirror via `app/services/tcgcsv.py`, one group fetch per set, **injected into the card dicts as a normal `tcgplayer.prices` block** and snapshotted — this runs BEFORE the catalog upsert (so the enriched dicts are what the catalog stores, and the app renders these cards as ordinarily TCGplayer-priced, variant tiles and all) and BEFORE the eBay pass (which only sees the remainder); unmatched sets are listed in the log (fix via `_GROUP_OVERRIDES`); matching is name-aware (`pick_candidate`) so numbers several products share resolve to the right card. Injection goes through `_apply_tcgcsv_block`, which marks the block `tcgplayer.priceSource = "tcgcsv"` — stopping the request-path 6h refresh from overwriting it with upstream's figure — and adds a direct `tcgplayer.url = tcgplayer.com/product/{productId}` buy link when the card has none (an existing url, upstream's own `prices.pokemontcg.io` redirect, is never overwritten), so TCGCSV-priced cards get working Buy-on-TCGplayer buttons. **Then `price_sanity_check`**: every card upstream DID price is cross-checked against the same TCGCSV mirror (all groups fetched, adding ~a minute); where the two headline prices diverge ≥3× on a name-and-number-matched product (`_SANITY_RATIO`; the name match is required — overriding a real price on a number-only match could price the wrong card), upstream's block is mapping the wrong product (observed July 23, 2026: swshp-SWSH066 served at the [Staff] promo's $580.92 vs the regular card's $98.49) or holding a junk figure ($19.99 for a ~$4k Shining Charizard), and TCGplayer's own number wins — the block is replaced (marked `priceSource`), `crawl.prices` corrected, and the day's snapshot re-recorded in place, all before the variant rows and catalog upsert read the dicts. **Then `image_fill`**: every crawled card's `images.small` URL is HEAD-checked (8 concurrent workers — but only URLs no run has verified before: a 200 stamps `verified` into the images block, which the catalog upsert and the request-path refresh carry forward, so each URL costs one check ever, not one per run). Where the check 404s — `images.pokemontcg.io` answers a missing card image with a 404 whose **body is a generic card-back PNG** that browsers render as if it were the artwork (every card of the 2014/15/17/18 McDonald's sets, which upstream has no scans for) — the whole images block is replaced with the TCGplayer product scan: `pick_candidate` on the same TCGCSV product match the price fills trust, `product_images` shaping small/large from the product's `imageUrl`, marked `source: "tcgplayer"`. Substituted cards fail the verified test next run and are re-checked, so upstream later adding a real scan heals back to it automatically; a 404 with no TCGplayer image leaves upstream's URLs in place (the frontend's `CardImage` detects the card-back and shows its placeholder). Skipped by `--no-tcgcsv` (substitutes come from the same mirror) and best-effort like the other passes. After those passes, `record_variant_snapshots` runs over every crawled card (post-fill, so injected variant blocks get series too) — multi-variant cards get one extra snapshot row per variant per day. Then the catalog upsert: every crawled card into `card_catalog` (best-effort — a catalog failure never costs the day's snapshots), **authoritative** (`keep_stored_prices=False`) whenever the TCGCSV fill ran — every dict carries fresh upstream data plus the fill's arbitration, so a card still without a prices block has no priceable source left and its stored block clears instead of fossilizing a retracted price (`--no-tcgcsv` or a failed fill keeps the protective default) — with a complete, un-truncated run stamping the `last_full_sync` marker that lets the app's list endpoints trust the catalog (`--max-pages` smoke runs and crawls with dropped pages upsert but never stamp). **Then `ebay_fill`, the last resort**, over only the cards TCGCSV couldn't match: scrapes each card's eBay sold listings (via the `ebay_prices` fetch/parse/summarize pieces — `_estimate_one` distinguishes a failed fetch from a fetched-but-saleless page, which `estimate()` can't) and snapshots the sold **median** — newest sets first (`set.releaseDate` desc), skipping cards `recorded_today` says are already done (so a same-day re-run spends its budget on new ground), pausing `--ebay-pause` seconds between scrapes (default 3), capped at `--max-ebay` estimates per run (default 500; `0` skips the pass). Saleless results are normal deep in the tail: they record nothing, stay gapped, and never stop the pass — only 5 **consecutive failed fetches** (the bot-block signature) end it early. **Then `recover_dropped`**, a final stage for **dropped pages** — pages pokemontcg.io couldn't serve even after every retry sweep, whose cards `_collect` never saw so they're in none of `crawl.cards/prices/unpriced` and neither fill above could reach them (a distinct gap from cards it served priceless). It diffs the catalog against this run's crawled ids — any card the catalog holds that this run didn't crawl is, barring a rare upstream deletion, exactly a dropped page's card — presents those cards to the same `tcgcsv_fill` matcher (as a mini-crawl of unpriced candidates), snapshots the TCGCSV price, and re-upserts the recovered cards so their catalog price refreshes too. So a page outage doesn't punch a hole in the day's history — the price comes from the independent TCGCSV mirror instead. Gated to a full (non-`--max-pages`), already-synced run and skipped by `--no-tcgcsv`: without a synced catalog "uncrawled" doesn't mean "dropped", and a brand-new card the catalog has never seen still waits for the next complete crawl (no set/number to match on until then). The run finishes by calling `history_archive.compact` to move months older than the daily window into cold storage (`--no-compact` skips it; a compaction failure is logged and never fails the run — rows just stay in the DB until the next attempt). Idempotent (per-UTC-day dedupe; `record_snapshots` refreshes same-day rows in place, so a TCGCSV price recorded at 1pm replaces the morning's eBay median rather than duplicating it). No FastAPI app needed — it uses `app.database.SessionLocal` + its own upstream session. `--max-pages N` limits the crawl for smoke tests. A full run is slow (upstream latency, not payload); it keeps its own `_PAGE_SIZE = 250` deliberately — it's a retrying batch job where throughput beats per-request latency, unlike the user-facing 50/page in `app/routers/cards.py`. Scheduled by a launchd LaunchAgent (see "Daily snapshot job" below).
- `app/services/history_archive.py` — cold storage that keeps `card_price_snapshot` from growing ~1.1GB/year, structured like stock-market data: the DB holds daily rows for the recent window plus one "monthly close" per card+variant per older month; the full old dailies live on disk. `compact(db)` finds complete months that ended more than `DAILY_WINDOW_DAYS` (30) ago, exports each to one gzipped CSV (`.archive/price-history/YYYY-MM.csv.gz`, ~3–6MB/month, columns card_id/variant/snapshot_date/price; `PRICE_ARCHIVE_DIR` env overrides the dir, tests point it at a temp dir) via atomic tmp+rename, then deletes the month's rows **except each card+variant's last** (the close — kept per variant so variant charts get monthly closes too). Ordering is strict: the file must exist on disk before any row is deleted, an existing file is never rewritten, and re-compacting an already-thinned month is a silent no-op. `restore_month(db, "YYYY-MM")` loads a month's archived rows back, skipping ones already present (archives written before the variant column restore as headline rows). Run automatically at the end of the daily snapshot job; `scripts/archive_history.py` is the manual CLI (bare = compact now, `--list`, `--restore YYYY-MM`).
- `scripts/backup.sh` — the nightly backup job for **non-Docker hosts** (plain bash; cron it like `10 3 * * * /path/to/Mintly/Backend/scripts/backup.sh >> /var/log/mintly-backup.log 2>&1`, after the day's snapshot job has compacted — production's Docker deploy instead runs a server-local dockerized equivalent, see "Production deployment"). Two things are backed up, because the DB alone no longer holds full price history: (1) a custom-format `pg_dump --no-owner` of `DATABASE_URL` into `BACKUP_DIR/db/mintly-YYYY-MM-DD.dump` — written to a temp file, checked readable with `pg_restore --list`, then renamed into place, one dump per UTC day (a same-day rerun overwrites); (2) an rsync mirror of `Backend/.archive/price-history/` into `BACKUP_DIR/price-history/` (deliberately no `--delete` — the source is append-only, so a bad/empty source can never erase already-backed-up months; missing dir = skipped, normal before the first compaction). Local dumps rotate after `BACKUP_KEEP_DAYS` (default 14); if `BACKUP_REMOTE` is set (an rsync destination like `user@host:/backups/mintly`) the whole `BACKUP_DIR` is copied off-server, else the run **warns** — a backup on the DB's own disk doesn't survive the disk. Config resolves environment-first, then plain `KEY=value` lines in `Backend/.env` (`BACKUP_DIR` default `~/backups/mintly`; `PG_BIN` prepends a dir to PATH for hosts where pg_dump isn't on it — this dev Mac needs `PG_BIN=/opt/homebrew/opt/postgresql@15/bin`, matching the running Homebrew postgresql@15). `DATABASE_URL` is never echoed. Restore: `pg_restore --clean --if-exists --no-owner -d "$DATABASE_URL" db/mintly-YYYY-MM-DD.dump`, then copy the archived CSVs back into `Backend/.archive/price-history/` (round trip verified July 21, 2026: restore into a scratch DB reproduced every table's row count exactly).
- `app/services/tcgcsv.py` — real TCGplayer prices from [TCGCSV](https://tcgcsv.com), a free nightly mirror of TCGplayer's catalog + price files (refreshed daily at 20:00 UTC), used by the snapshot job to price the cards pokemontcg.io returns with an empty `tcgplayer.prices` block (it lags on brand-new sets). `group_id_for_set(set_name, set_id)` matches a pokemontcg.io set to a TCGplayer "group" by normalized name (their names carry a `"ME05: "`-style code prefix that's stripped; accents folded, so "Pokémon GO" matches "Pokemon GO"; `_GROUP_OVERRIDES`, keyed by pokemontcg.io set id, wins for stubborn mismatches — it covers the base sets whose TCGplayer names add "Base Set", the HS/promo/McDonald's sets, and both EX Trainer Kits — add entries as unmatched sets appear in the job log; only "Pokémon Futsal Collection" has no TCGplayer group at all). `candidates_for_group(group_id)` joins the group's products (card number from the `extendedData` `"Number"` entry; sealed products have none and are skipped — important, since a Booster Box carries real "Normal" prices) with its price rows, keyed by normalized number (`norm_number`: part before `/`, leading zeros stripped, case-folded — `"001/084"` → `"1"`, `"TG12/TG30"` → `"tg12"`), `subTypeName` mapped to the pokemontcg.io variant keys (`Normal`→`normal`, `Reverse Holofoil`→`reverseHolofoil`, …), rows with neither `marketPrice` nor `midPrice` dropped — one entry PER PRODUCT, since TCGplayer sells several products under one number ([Staff] prerelease stamps beside the regular promo; different cards sharing a number in merged groups like the EX Trainer Kit half-decks and WoTC promos). `pick_candidate(candidates, card_name, require_name=False)` chooses among them: candidates whose product name (before the " - <number>" tail) matches the card's name, then the ones without a bracketed qualifier (a [Staff] stamp is a different, rarer physical card), then the shortest name — deterministic, so the plain version always wins; `require_name=True` (the sanity check's mode) returns None instead of settling for a number-only match. It returns the whole product entry — name, `prices`, `image` (each candidate carries the products file's `imageUrl`, the TCGplayer product scan), and `productId` (the TCGplayer product id, which the snapshot job turns into `tcgplayer.com/product/{id}` buy links) — and `pick_product` is its prices-only view, so prices, images, and links always come from the same chosen product. `product_images(candidate)` shapes that scan into a pokemontcg.io-style images block for the snapshot job's image check: `small` = the listed `_200w.jpg` rendition, `large` = the `_in_1000x1000.jpg` suffix swap (asks the CDN for its largest — old promo products only have ~200px scans, which the CDN then serves), marked `source: "tcgplayer"`. `prices_for_group(group_id)` keeps the flat {number: variants} view with duplicates resolved to the base product; `card_prices(set_id, set_name, number, card_name=None)` is the one-card convenience — pass the name whenever it's known. Returned dicts are `tcgplayer.prices`-shaped, so `extract_price` and the frontend consume them unchanged. Groups list and per-group joins are memoized per process (the job is one process per day); failures aren't cached, so a later call can retry. Best-effort throughout — any fetch/parse failure returns empty/`None`, never raises. tcgcsv.com answers 401 to the default python-requests user agent — the module session sends an identifying `Mintly/1.0` UA (verified July 21, 2026). Batch-only by design: nothing on the request path calls it.

### Data model
- `users` — id, email, username, hashed_password (bcrypt), created_at, accepted_terms_at (when the user accepted the ToS at registration; NULL for accounts predating the requirement). Deleting an account (`DELETE /auth/me`) removes this row, the user's `portfolio_cards`, and their `password_reset_tokens`; the shared `card_price_snapshot` rows aren't user-scoped, so they stay.
- `portfolio_cards` — one row per **purchase (lot)**: user_id, card_id (TCG API id like `base1-4`), card_name, quantity, purchase_price, purchase_date. The same card bought twice = two rows; the frontend groups them visually.
- `password_reset_tokens` — a pending "forgot password" link: user_id (FK, indexed, no cascade — account deletion clears rows explicitly), token_hash (unique — the sha256 of the emailed token; the raw value never touches the DB, so a DB leak can't yield working links), created_at, expires_at (30 min out), used_at (NULL until consumed; a used row stays so the link can't replay). At most one live row per user — a new request deletes the old ones. (Migration `f3a9c15e8d72`.)
- `card_catalog` — one row per card, the local mirror of the upstream catalog the app browses from: card_id (PK), searchable columns (name, number, set_id, rarity, `|`-delimited types, release_date) extracted for querying, `data` (JSON — the card dict exactly as served to the frontend; its `images` block may carry the daily job's arbitration markers — `verified`: the URL HEAD-checked live once, or `source: "tcgplayer"`: a substituted product scan for a URL upstream 404s), and `price_updated_at` (when `data`'s tcgplayer block was last fetched; past 6h it's re-fetched in the background on view). Written by the daily crawl and by every proxy fallback.
- `catalog_meta` — key/value bookkeeping; the single `last_full_sync` row records when a complete crawl last finished, and its existence is what lets list endpoints serve from `card_catalog`.
- `card_price_snapshot` — one row per card per **variant** per UTC day: card_id, variant, price, snapshot_date. `variant` `""` is the **headline series** — the preferred-variant price `extract_price` picks, which every existing feature (daily change, estimates, portfolio history) reads; named variants (`"holofoil"`, `"reverseHolofoil"`, …) are recorded alongside it **only for cards with 2+ priced variants** (a single variant would just duplicate the headline), powering the per-variant chart lines and table changes. Shared across users, with a composite `(card_id, snapshot_date)` index. Written by the daily `scripts/snapshot_all.py` job (every TCGPlayer-priced card, then a TCGCSV fill for cards pokemontcg.io leaves unpriced, then a capped eBay-median fill for the remainder — the row doesn't record which source it came from), and also whenever any user loads their portfolio **or browses a priced card** through a card endpoint (all deduped per UTC day). It is the app-wide price-history store; portfolio value-over-time is derived from it by filtering to a user's holdings (`/portfolio/history`) — headline rows only, so there is no separate portfolio-snapshot table. Retention is tiered like stock-market data: the table holds daily rows for roughly the last 30–60 days plus one monthly-close row per card+variant per older month (~36MB/year before variants); the complete old dailies are offloaded — not deleted — to gzipped CSVs by `app/services/history_archive.py`. (Renamed from `portfolio_snapshot` — migration `b7e1c4d9f2a3`; `variant` added by `d4f8a21c7e56`, backfilling every pre-existing row as headline via the `''` server default.)
- All `DateTime` columns store **naive UTC**, set via the shared `utcnow()` helper in `app/models.py`; anything compared against them (e.g. the snapshot dedupe in `app/routers/portfolio.py`) must use `utcnow()` too, never local time. They serialize without a zone suffix, so the frontend must anchor them with `Z` before parsing (`parseUTCDate` in `Portfolio.tsx`) — a bare `new Date(...)` reads them as local time and shows evening purchases dated tomorrow.

### Smart search (`/search`)
Lowercases and tokenizes the query (upstream matching is case-insensitive, so "Charizard" and "charizard" must build the same query string and share one cache entry — `/cards` likewise lowercases `name`/`set_id`, but `rarity`/`type` stay exact: era-specific dropdown strings), then:
1. Digits → card number; letters+digits (e.g. `swsh11`) → set id; rest → name words.
2. Scans name words for a real **set name** (longest contiguous match against the cached sets list) — "pikachu lost origin" → `name:"pikachu" set.id:swsh11`.
3. Name is always quoted (unquoted multi-word queries are a syntax error upstream → HTTP 400).
4. If nothing matches, retries dropping words from the front, then the back — "sleepy pikachu" falls back to "pikachu". "Nothing matches" means `totalCount == 0`, not an empty page — so requesting a page past the end of a valid query doesn't trigger the fallback.

The parse is shared by both execution paths: once the catalog is synced, the whole flow — including the word-drop fallback — runs as local DB queries (name filters become case-insensitive substring matches, so quoting gotchas can't reach upstream); only a catalog answer that is empty after every fallback retries the original query upstream (cached), and those results are upserted into the catalog.

### Frontend styling
- **CSS Modules, co-located.** Each component and page has a `*.module.css` beside it holding its own styles (imported as `styles`, applied `className={styles.camelCase}`; `vite.config.ts` sets `css.modules.localsConvention: 'camelCase'`, so the CSS files keep kebab-case names while components read clean camelCase). Class names are hashed and scoped, so styles can't leak between components. `src/App.css` is now only the **global/shared** layer (~240 lines): the app shell (`.main`/`.page`/`.centered`), buttons, the shared filter/card-tile/add-form primitives, utilities (`.positive`/`.negative`/`.error`/`.prices-note`), the legal-page styles, and the `day-change-*` chip (its direction classes are built with dynamic names, so the whole family stays global). `index.css` holds the design tokens (CSS variables) and reset. Rule of thumb: a class used by **one** component lives in its module; a class shared by **two or more** stays global. Overrides that cross the boundary use `:global()` — e.g. `Portfolio.module.css` styles the shared button as `.card-actions :global(.btn-outline)`, and `CardDetail.module.css` tweaks the shared `PriceQtyForm` fields via `.detail-add-form :global(.edit-field)`. The shared presentational components (`DayChange`, `GainLoss`, `StatRow`, `StatusMessage`, `PriceQtyForm`, `PageMessage`) intentionally have **no** module — their classes are part of the global shared vocabulary.
- **Fluid/intrinsic layout, not breakpoints.** The catalog grid, portfolio stats, and home features reflow on their own with `repeat(auto-fill|auto-fit, minmax(min(100%, clamp(…)), 1fr))`, and typography/spacing scale with `clamp()`. This handles any viewport — a folded phone (~280px) through iPad and tablet split-screen up to desktop — with no device-specific media query, so unusual widths and foldables just work; the `min(100%, …)` inside each `minmax` is the overflow guard for very narrow screens. The single deliberate breakpoint is the navbar in `Navbar.module.css`: it can't flow like a grid (brand + centered pill + auth button), so it compacts in steps — ≤768px shrinks the pill/button, ≤380px drops the "Mintly" wordmark to just the leaf logo, ≤340px tightens further for split-screen. Wide data (the card-detail price table) sits in an `overflow-x:auto` box so it scrolls within its column instead of widening the page; flex-wrapped inputs carry `min-width: 0` so they shrink rather than overflow. Verified with no horizontal overflow from 300px through 1280px on every page.

Live at **https://mintlytcg.com**, served from `pikachuserver` — a Dell laptop running Ubuntu Server 24.04 on the home network (Wi-Fi only; reachable from the dev Mac via `ssh pika`, remotely via Tailscale). The stack is Docker Compose in `~/apps/mintly` (a clone of this repo); `docker-compose.yml`, `Caddyfile`, and `Backend/Dockerfile` are checked in at the repo root.

| Service | Image | Role |
|---|---|---|
| `db` | `postgres:16-alpine` | data in the `pgdata` named volume |
| `api` | built from `Backend/Dockerfile` | uvicorn `app.main:app`, **one worker deliberately** — the rate limiter and price caches are in-memory per process, so more workers would multiply every rate budget and scrape independently |

No router port-forwarding, and no DNS record contains the home IP — the origin accepts no inbound connections. LAN/Tailscale devices can still reach caddy directly (`http://pikachuserver`).
- **Frontend build** happens on the server (`cd Frontend/mintly && npm ci && npm run build`) using the committed `.env.production` (`VITE_API_BASE=/api` — same-origin through Caddy, so CORS never triggers).

The compose service injects the whole file via `env_file: .env`, so a new backend env var needs no compose edit — add the line and `docker compose up -d api` (recreates on env change).

## Daily snapshot job

`scripts/snapshot_all.py` records a price snapshot for every card so history is gap-free, and refreshes the `card_catalog` table the app browses from (TCGPlayer prices → TCGCSV fill for the unpriced → image check (unverified image URLs HEAD-checked, dead ones re-pointed at TCGplayer scans) → catalog upsert → eBay-median fill for whatever TCGCSV couldn't match — the eBay pass at the default 3s `--ebay-pause` is polite scraping whose length depends on how many cards TCGCSV leaves over — then compacts months older than 30 days into `Backend/.archive/price-history/`). In production it runs via the server's 20:00 UTC cron inside the api container (see "Production deployment"). On this dev Mac it runs daily at **1:00pm local** against the local dev DB via a launchd LaunchAgent (`~/Library/LaunchAgents/com.mintly.daily-snapshot.plist`) — 13:00 PDT = 20:00 UTC / 13:00 PST = 21:00 UTC, i.e. on/just after TCGCSV's daily 20:00 UTC refresh, so the fill reads same-day prices (the crawl's 30–90 min of pokemontcg.io paging runs before the first TCGCSV fetch, adding propagation buffer). Output goes to `~/Library/Logs/mintly-daily-snapshot.log`. It needs the Postgres in `DATABASE_URL` running; if the Mac is asleep at 1pm, launchd runs it on the next wake.

**macOS TCC / Full Disk Access (required).** The repo lives under `~/Documents`, which macOS protects — a launchd job can't read files there by default, so a scheduled run fails immediately with `Operation not permitted`. The plist therefore invokes the **framework Python directly** (`/Library/Frameworks/Python.framework/Versions/3.14/bin/python3.14`, which is outside `~/Documents` so launchd can exec it), with `PYTHONPATH` pointing at the repo venv's `site-packages` and `WorkingDirectory` set to `Backend/` (so `.env` loads; the script itself puts `Backend/` on `sys.path` to import the `app` package). That python binary must be granted **Full Disk Access** so it can read the project:
1. System Settings → Privacy & Security → Full Disk Access → **+**
2. In the file dialog press **⌘⇧G**, paste `/Library/Frameworks/Python.framework/Versions/3.14/bin/python3.14`, add it, and toggle it **on**.
3. `launchctl kickstart gui/$(id -u)/com.mintly.daily-snapshot` and confirm the log shows `page 1/82 …` instead of the permission error.

(Alternative to granting FDA: move the repo out of `~/Documents`, e.g. to `~/GitHub`, and repoint the plist — then no special permission is needed.)

Managing it:
```bash
launchctl load   ~/Library/LaunchAgents/com.mintly.daily-snapshot.plist   # enable
launchctl unload ~/Library/LaunchAgents/com.mintly.daily-snapshot.plist   # disable
launchctl kickstart gui/$(id -u)/com.mintly.daily-snapshot                # run now
launchctl kill  TERM gui/$(id -u)/com.mintly.daily-snapshot               # stop a run
launchctl list | grep mintly                                             # status (col 1 = PID if running, col 2 = last exit)
tail -f ~/Library/Logs/mintly-daily-snapshot.log                         # watch output
```
The plist is machine-specific (absolute paths) and lives outside the repo; the job script is in `Backend/scripts/`. To change the time, edit `StartCalendarInterval` in the plist and `unload`/`load` it. To run it by hand from a terminal (which already has Documents access), just `cd Backend && venv/bin/python scripts/snapshot_all.py`.

## Behaviors worth knowing

- **Browsing is served from the local card catalog**: once the daily crawl has completed once (the `last_full_sync` marker), search/filter/set/detail requests read `card_catalog` in milliseconds instead of waiting on the upstream API, and keep working through upstream outages. Prices shown while browsing are at most ~6h old — a viewed card or list page with an older stored price is served instantly while a background thread re-fetches it (detail responses carry `refreshing: true`, which CardDetail re-polls on until the fresh number lands; list pages just serve fresher data to the next request). The portfolio's live 15-minute batched price fetch keeps P&L fresher than the catalog, but where upstream has no price (newest sets) it now falls back to the catalog's TCGCSV price, then the latest eBay-median snapshot — so a held newest-set card tracks the same value the browse pages show instead of a blank price. Brand-new sets reach users through the proxy fallback (upserted as they're browsed) until a crawl completes them; catalog results order newest-sets-first with name matching as case-insensitive substrings.
- **Price picking**: first available `market` (falling back to `mid` when the variant has no market value) among holofoil → normal → reverseHolofoil → 1stEditionHolofoil (`extract_price` backend, `getCardPrice` frontend — keep in sync). Snapshots recorded before July 15, 2026 used `mid`, so long price-history series have a small step at the switchover.
- **History chart**: computed against *current* holdings, so editing a quantity retroactively changes past points. Snapshots only record on days someone loads their portfolio. With <2 days of data the chart shows a flat placeholder line at today's value. Snapshot days are UTC, so a late-evening US visit records under the next calendar day's UTC date — the chart's newest point can read one day ahead of local; dedupe and chart bucketing use the same UTC day, so points stay one-per-day.
- **Newest sets can lack TCGPlayer prices upstream — TCGCSV fills them**: the pokemontcg.io API lags on 2026 "Mega Evolution" era sets (was 0/N for me4, me3, me2pt5; it backfills over time — `me1` is now fully priced upstream). The daily job closes that gap with real, variant-separated TCGplayer prices from the TCGCSV mirror, injected into the catalog rows — so after one run those cards browse, chart, and add exactly like ordinarily-priced cards (variant tiles included), instead of showing a noisy eBay median (eBay can't separate variants and has a price floor that made a 4¢ common show as ~$4). The "prices unavailable" UI note and blank-price add rejection still exist for cards no source can price; a card browsed before the crawl has enriched it still uses the live eBay fallback. Source priority: pokemontcg.io's own TCGplayer figure → TCGCSV → eBay — with one guard: the daily job's `price_sanity_check` overrides an upstream figure that diverges ≥3× from TCGplayer's own mirror for the name-matched product (upstream occasionally maps a card to the wrong product, e.g. a [Staff] promo, or serves a junk figure), and the `priceSource` mark keeps the 6h background refresh from putting the bad number back.
- **eBay fallback for priceless cards (last resort, after TCGCSV)**: `/cards/{id}/ebay-price` estimates a value from recent *sold* eBay listings for cards TCGPlayer can't price. CardDetail shows it and pre-fills the add form with the median, so those cards are still addable. The estimate is the median/average of the most recent ~25 ungraded single-card sales, with graded slabs/lots/proxies excluded by title and far-off outliers trimmed around the median. eBay markup and bot checks change, so treat `count:0` as normal, not an error. Verified live (e.g. Mega Lucario ex 188 → ~$250 median from ~20 recent sales). The daily snapshot job records the same estimator's **median as the card's history snapshot** only for priceless cards its TCGCSV fill couldn't match (capped per run, newest sets first) — so their charts and `DayChange` chips work too, and **search/set tiles show that stored median** styled like a normal price with a muted "eBay est." label and the usual daily-change chip (`attach_estimates` on every card response — reading snapshots, never live-scraping on browse; the chip appears once a card has two snapshot days, same rule as priced cards). On the card detail page the live `/cards/{id}/ebay-price` scrape *does* refresh today's snapshot to the freshly-scraped median (guarded to priceless cards), and CardDetail overlays that same median onto the chart's newest point — so an eBay card's graph and its stored history both stay in step with the estimate shown above the chart, mirroring how `record_snapshots` keeps a TCGPlayer card's day point current. A card's history can therefore mix sources: eBay medians while TCGPlayer is blank, switching to TCGPlayer market once upstream backfills (like `me1` did) — expect a step at the switchover, same as the July 15, 2026 mid→market one.
- **Daily price change**: any priced card browsed through a card endpoint gets a snapshot, and responses carry `priceChange` (`{amount, percent, since}` vs the card's `change_baselines` baseline — the most recent prior-day snapshot, stepping one day further back when that close already equals the current price, since a day's row is refreshed in place and would otherwise pin every chip at $0.00 from the UTC rollover (5pm PDT) until the next crawl lands; `since` names the day actually compared against). `/portfolio` rows carry the same as `price_change`, and CardDetail's per-variant Today chips apply the same rule client-side. The frontend renders it as a `DayChange` chip next to the price — so a card's daily move is visible without opening or adding it. It's absent until at least one prior-day snapshot exists for that card.
- **Per-card price history**: `/cards/{id}/history` returns Mintly's own daily snapshots (there is no upstream history endpoint). The daily `scripts/snapshot_all.py` job records a point for every TCGPlayer-priced card each day (every priceless card is attempted via the eBay fill too, but only those with ≥3 recent ungraded sales actually record a point — the rest stay gapped), so charts fill in one day at a time for the whole catalog going forward — but depth is still bounded by how long the job has been running (snapshots start July 14, 2026), so charts are short until it accumulates. The default window is ~5 years; the chart shows a "not enough history yet" note with fewer than two points. **Resolution is tiered, stock-chart style**: daily points for roughly the last 30–60 days, then one point per month (each card's month-end close, thanks to `history_archive` compaction) — so the 1M range stays daily while 6M/1Y/All go monthly as data ages. Recharts just connects the sparser points; nothing in the frontend knows about the tiers. `/portfolio/history`'s carry-forward likewise rides monthly closes for old dates.
- **Per-variant price history**: cards with 2+ priced TCGPlayer variants get one snapshot per *variant* per day alongside the headline row (recorded by the daily job and on browse), served as the `variants` map in `/cards/{id}/history`. CardDetail's chart renders them as one colored line per variant (fixed color per variant name, legend + line-end labels) and the variants table adds a per-variant daily-change chip. Variant rows only started accumulating July 21, 2026, so on day one a non-preferred variant shows as a single dot; the preferred variant's line carries the full pre-variant history (the headline series *was* that variant — `mergeHeadline` in `variants.ts` splices it in client-side). Single-variant cards record no variant rows (their one variant is the headline) and keep the original area chart.
- **Add button** shows "Adding…" and blocks double-clicks (the add round-trips to the external API, 1–3s).
- **Structured data is client-rendered and honesty-first**: all JSON-LD is injected by React (Googlebot executes JS, so it sees it; verified live — a card page serves the site `@graph` plus a `Product` block with name/image/description/sku/brand and no `offers`). Markup only ever describes what's visible on the page: the per-card `Product` block carries no `offers` at all (Mintly is a tracker, not a store — the market/estimate prices shown are third-party figures, not Mintly listings), and descriptions mirror the on-page copy — Google treats markup for hidden/misleading content as spam. Non-JS crawlers see only the static `index.html` title/description; prerendering or SSR would be needed for them (see next steps). Crawler discovery is handled by `robots.txt` → `GET /sitemap.xml`, which lists every catalog card's detail page.
- **Rate limits are sized for humans, walls for scripts**: a browsing user never sees them (debounced search + pagination stays far under 120/min), but a scraper burning the upstream API quota, a credential-stuffing loop, or an eBay-estimate hammer hits a 429 fast. Login attempts count toward the limit whether they succeed or fail — after 10 in 5 minutes even the correct password gets a 429, which is the point (a brute-forcer's lucky guess is blocked too). The login form surfaces the 429's "try again in about Ns" detail instead of "Invalid credentials" (`login()` in `api.ts`), so a locked-out user isn't sent hunting for a typo. Budgets are per-process and reset on restart, same as the other in-memory caches.
- **Registration has no email verification** — an accepted v1 trade-off, not an oversight: any address registers an account without proving ownership, so fake signups are possible; the 10/hour/IP register rate limit keeps bulk abuse bounded. Two consequences to keep in mind: a typo'd (or someone else's) email means password reset — which only ever mails the stored address — goes to the wrong inbox, and nothing ties accounts to real people. Adding verification later means a token flow like password reset's plus an `email_verified_at` column.
- **Session expiry**: JWTs last 7 days. Any authed call after expiry gets a 401 → token cleared → redirect to `/login` with a "session expired" notice (`SessionExpiredError` in `api.ts`, redirect via `useSessionRedirect` in `hooks.ts`).
- **Account management**: the Profile page (`/profile`) is where a user views/edits their username + email (`PATCH /auth/me`) and changes their password (`POST /auth/me/password`, which verifies the current one). Username/email changes are validated for uniqueness against other users; changing the username doesn't invalidate the JWT (its `sub` is the user id, not the name).
- **Admin dashboard**: `/admin` shows site-wide stats (user counts, a 30-day signups chart, portfolio totals, catalog/snapshot health, DB size, recent signups) to accounts whose email is listed in the `ADMIN_EMAILS` env var — config, not schema, so granting/revoking admin is an env edit + api restart, no migration. Everyone else — logged out, expired session, or logged in but not listed — sees the exact same "Page not found" view the `path="*"` catch-all shows for any unknown URL (no login prompt, no session-expired redirect: those would reveal an authed page exists), and the only link to it (the Profile header's Admin button) renders only for admins — to anyone not on the list, `/admin` is indistinguishable from `/taco`. One subtlety of keying on email: admin rides on whatever account owns that address, and changing the account email (`PATCH /auth/me`) away from the listed one drops admin on the next `/auth/me` read. Since email addresses aren't ownership-verified at registration, only list addresses already registered to yourself.
- **Password reset**: a forgotten password is recoverable via Login's "Forgot password?" → `/reset-password` → emailed single-use link (30-min expiry, token stored hashed, enumeration-safe generic response — see `app/routers/auth.py`). **Production emails send for real via Resend** (see "Production deployment"); a dev machine without `SMTP_HOST` in `Backend/.env` prints the "email" to the uvicorn console instead — the deliberate dev mode, grab the link from the terminal. A reset doesn't invalidate existing JWTs (stateless, 7-day expiry — same as an authed password change).
- **Account deletion**: `DELETE /auth/me` (authed) permanently removes the user and their portfolio lots — the shared per-card snapshots stay (not user-tied). The **Profile** page's "danger zone" (`DeleteAccount`, moved off Portfolio) drives it behind a two-step, typed-"DELETE" confirm (no native `confirm()`), then logs the user out to `/login` with an "account deleted" notice. `Terms.tsx` §2 and `Privacy.tsx` §5 document the right; `Privacy.tsx` §6 is the contact address (mintlytcg@gmail.com).
- **Accessibility preferences**: the Profile page's Accessibility card toggles reduce-motion, high-contrast, underline-links, and text size. They're browser-local (`accessibility.ts` → localStorage → `<html>` `data-*` attributes → `index.css`), apply instantly, survive reloads, and are never sent to the server — so they don't roam across devices and aren't part of account data. Reduce-motion also honors the OS `prefers-reduced-motion` setting even before a visit.
- **Upstream latency scales with the requested `pageSize`, not the payload**: benchmarked (July 16, 2026) `pageSize=250` at 20–60s with dropped connections vs `pageSize=50` at 2–5s — for near-identical payload sizes (~35–40KB). Hence `_PAGE_SIZE = 50` in `app/routers/cards.py`; don't raise it without re-measuring. This now only applies to the proxy fallback path — a search that misses the catalog (unsynced DB, zero-result query, brand-new set) costs a few seconds (measured 2.8s cold, ~8ms warm); expired cache entries never block — they're served stale while a background thread refreshes (up to 24h, then synchronous again) — and the cache survives restarts via its disk mirror, so only genuinely never-fetched queries pay the cold cost. Portfolio loads are one batched call regardless of collection size (measured ~0.8s cold, ~4ms warm for 5 cards).
- **Upstream is occasionally flaky, not just slow**: observed (July 10, 2026) `GET /sets` transiently returning 404 and taking ~50s when it did succeed. All upstream calls now carry a (5s connect, 60s read) timeout so a hung connection can't pin a worker, and the sets list is served stale at **any** age while a background thread refreshes — no request ever waits out a sets re-fetch, and `/search`/set pages keep working through flakes as long as the sets list has been fetched once ever (it persists to disk across restarts). A flake on a genuinely cold cache (first run ever) still surfaces as `{"detail": "Failed to fetch sets"}`; there is no retry, only the next request trying again. `fetch_prices` skips failed/timed-out chunks, so `/portfolio` degrades to missing prices instead of erroring. Once the catalog is synced, browsing doesn't touch upstream at all — flakes only affect the fallback paths and background price refreshes (which just leave rows stale for the next attempt).
- **Historic merged rows**: before lots existed, duplicate adds were averaged into one row. Those can't be un-averaged; new purchases keep exact prices.
- **Card image URLs can't be guessed from card ids — and dead ones are actively repaired**: newer sets (Mega Evolution era) are hosted on `images.scrydex.com`, and `images.pokemontcg.io` answers a missing image with a **404 whose body is a card-back PNG** — a browser `<img>` renders the body and never fires `onerror`, so unhandled it shows the back as if it were the artwork (upstream has no scans at all for the 2014/15/17/18 McDonald's sets). Two layers handle it: the daily job's `image_fill` HEAD-checks each crawled card's image URL once (status codes are exact) and re-points 404ing cards at the TCGplayer product scan from TCGCSV (`images.source: "tcgplayer"`; ~200px for old promos — soft on the detail page, but a real front; re-checked each run, so upstream growing a scan heals back), and `CardImage` treats a loaded image with the 404 body's fixed 640×892 natural size as failed (genuine smalls are 245×342, hi-res 734×1024), showing its placeholder for anything the crawl hasn't repaired yet. `/portfolio` returns each row's real `image_url` (fetched alongside prices, same cache); the frontend's `getCardImageUrl` guess is only a fallback. All card artwork renders through the shared `CardImage` component, which reserves the 5:7 card ratio (so the grid never shifts as images load) and degrades a failed or missing image to a muted card-shaped placeholder instead of a blank gap or broken-image icon.
- **Rarity names are era-specific** exact strings (old: "Rare Holo"; Scarlet & Violet: "Double Rare") — a rarity filter + wrong-era set legitimately returns nothing.

## Gotchas for developers

- Run `npm`/`eslint` commands from `Frontend/mintly/`, not the repo root.
- A fresh database proxies all browsing upstream until `scripts/snapshot_all.py` completes once and stamps the sync marker — slow searches on a new environment mean the catalog isn't populated yet, not a regression. Truncated (`--max-pages`) or partially failed crawls upsert cards but deliberately never stamp it.
- The eslint react-hooks rules are strict (v7): no synchronous `setState` inside `useEffect` — defer via promise callbacks or timeouts (see `Search.tsx`/`CardDetail.tsx`), or remount the component with a `key` so its state re-initializes instead of being reset in the effect (see `PriceHistoryChart`).
- Every backend file save restarts the dev server; the card/search response cache is restored from its disk mirror, but the portfolio price cache is memory-only → the first portfolio load after a restart is slow.
- CSS Modules typos fail silently: a mis-keyed `styles.foo` resolves to `undefined`, so the element renders with no class and no error (TS types module classes as `string`, so it can't catch a wrong key). After any styling change, check the page in the browser, not just `npm run build`. Only genuinely shared classes remain as plain strings in JSX and must exist in `App.css`; everything else goes through a module's `styles` object.
- Card searches only return the fields listed in `_CARD_FIELDS` (`app/routers/cards.py`). If the frontend `Card` type grows a field, add it there too or it will arrive undefined. (`priceChange` is added server-side in `_with_price_changes`, not selected upstream.)
- eBay scraping (`app/services/ebay_prices.py`) needs a two-step request (homepage for cookies, then the search with a Referer) — a bare request gets a tiny "Error Page | eBay". When changing `parse_sold`, verify against a freshly fetched sold-listings page: `.su-card-container` tiles, title in the image `alt`, and the price *after* the "Sold <date>" caption.
- `Backend/.env` holds real secrets and is gitignored — never commit it or move its values into query strings/logs.
