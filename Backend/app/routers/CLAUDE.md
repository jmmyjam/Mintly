# Backend routers — `Backend/app/routers/`

FastAPI HTTP routers. Global rules live in the repo-root `CLAUDE.md`; backend-wide commands, data model, conventions, and gotchas in `Backend/CLAUDE.md`; the services these call in `Backend/app/services/CLAUDE.md`.

- `Backend/app/routers/health.py` — `GET /health`, the probe an uptime monitor should ping: runs `SELECT 1` through the request's DB session and answers `{"status": "ok"}`, or 503 `database unavailable` when the query fails — so a live process in front of a dead Postgres still trips the monitor (pinging the site root would only prove the static frontend serves). Unauthenticated and deliberately outside every rate-limit scope: a monitor polling every 5 minutes must never see a 429, and the probe costs one trivial query.
- `Backend/app/routers/sitemap.py` — `GET /sitemap.xml`, the crawler-facing URL list: the public static pages (`/`, `/search`, `/terms`, `/privacy` — authed pages are deliberately absent, crawlers only see their login prompt) plus one `/card/{id}` entry per `card_catalog` row (ordered by card id), each URL built on `FRONTEND_BASE_URL` (the same env var reset links use, so one setting names the site everywhere). Catalog reads are wrapped best-effort — a DB hiccup still serves the static pages, never a 500. Registered under the shared `"api"` rate-limit scope (120/min, one budget with the cards/portfolio routers). `Frontend/mintly/public/robots.txt` (copied into `dist/` by Vite) allows all crawling and points at `https://mintlytcg.com/sitemap.xml`; the Caddyfile routes `/sitemap.xml` to the api container so the sitemap serves from the site root, where that reference expects it.
- `Backend/app/routers/admin.py` — `GET /admin/stats`, the admin dashboard's numbers: read-only aggregate queries over the app's own tables (no upstream calls, nothing mutated). Users (total, new 7d/30d, with a portfolio), signups per UTC day over the last 30 days (zero-filled, for the dashboard's bar chart), the 10 most recent signups with per-user lot counts, portfolio totals (portfolios, lots, distinct cards, summed quantity), catalog health (row count, stale-price count vs `card_catalog.PRICE_TTL`, the `last_full_sync` value), snapshot health (total rows, headline rows today, newest snapshot), and `pg_database_size` (best-effort — `null` on SQLite/tests, wrapped in rollback so a failure can't poison the session). Gated by `get_admin_user`: a valid JWT whose account `app/services/admin_access.py` doesn't recognize gets a plain **404, not 403** — probing the URL reveals nothing; keep it that way. Registered under the shared `"api"` rate-limit scope. (Who counts as admin lives in `app/services/admin_access.py` — see the services file.)
- `Backend/app/routers/cards.py` — card/set endpoints + smart search, served **catalog-first**: once a complete crawl has stamped the sync marker (`catalog_meta.last_full_sync` — checked per request via `card_catalog.is_synced`), `/search`, `/cards`, and `/sets/{set_id}/cards` are answered straight from the `card_catalog` table (single-digit ms, no upstream call), and `/cards/{card_id}` always prefers a catalog row when one exists. Catalog answers order newest-sets-first (release date desc, then natural card-number order) and match names as case-insensitive substrings. The upstream proxy below remains the fallback for: an unsynced catalog (fresh DB), zero-result queries (typos, or sets newer than the last crawl), unknown single cards, and sets the catalog holds incompletely (`set_count` < the sets list's `total` — a half-crawled set must never serve confidently-short pages); fallback results are upserted back into the catalog (`_upsert_results`, best-effort), so new sets converge before the next crawl. **Stale prices refresh in the background**: a catalog row whose `price_updated_at` is past `card_catalog.PRICE_TTL` (6h) is served instantly anyway — `/cards/{card_id}` adds `refreshing: true` (the frontend re-polls on it) and list pages batch their stale ids — while `_refresh_prices_in_background` re-fetches via one `id:"…" OR …` upstream call (`refresh_card_prices` is the synchronous, testable core; per-id-set dedupe through `_refreshing`; a failed refresh just leaves the row stale for the next view). All catalog access is wrapped best-effort: a DB hiccup drops to the proxy, never a 500. The proxy path keeps its response cache (covers searches, single-card lookups, and the sets list, keyed per query+page). Cache entries are **stale-while-revalidate**: fresh for 6h (`_CACHE_TTL`), then served immediately while one daemon thread per key re-fetches in the background (`_refresh_in_background`; a failed refresh leaves the stale entry for the next attempt); past 24h (`_STALE_TTL`) the entry is dead and the fetch is synchronous again. Every cache write is also **mirrored to disk** (`Backend/.cache/cards`, gitignored; `CARD_CACHE_DIR` env var overrides — tests point it at a temp dir) as one JSON file per key (hashed filename, atomic temp-file + rename, best-effort — a failed write only costs persistence) and restored at startup by `_load_persisted_cache`, which prunes entries past `_STALE_TTL` and drops corrupt/interrupted files — so `--reload` restarts don't start cold. Cache files are `.json`, which uvicorn's reload watcher (`*.py` only) ignores. Card-list endpoints are paginated: they take `?page=` and return an envelope `{data, page, pageSize, totalCount}` at 50 cards/page (`_PAGE_SIZE` — upstream latency scales with the requested page size). Card searches pass `select=` upstream (`_CARD_FIELDS`) so responses carry only the fields the frontend uses. `/sets/{id}` is answered from the cached sets list with no upstream call. Every card-list and card-detail response goes through `_with_price_changes`, which records a daily price snapshot, attaches a `priceChange` object to each priced card, and attaches `estimate` (`{value, date}` — the card's latest snapshot, which for TCGPlayer-priceless cards is the daily job's eBay sold-median) to cards with no market price (see `price_history.py`); this is wrapped in try/except so a DB hiccup never breaks the card proxy. Also serves `/cards/{id}/history` (`{points, variants}` — the headline daily series plus one series per TCGPlayer variant for multi-variant cards) and `/cards/{id}/ebay-price` (eBay estimate). Upstream calls use a (5s connect, 60s read) timeout. The sets list is **stale-while-revalidate at any age**: it sits on hot paths (smart search's set-name matching, the set-page completeness check), so an expired copy is served immediately while one background thread re-fetches — a request never blocks on the observed 50s upstream sets hangs; only a truly cold cache (first run ever) fetches synchronously and can 504. All routes sit behind the router-level `"api"` per-IP rate limit (120/min, shared with the portfolio router); `/cards/{id}/ebay-price` adds a stricter `ebay` scope (60/hour) because each uncached estimate is a live eBay scrape. Synthetic variety ids (`tcgcsv.is_variety_id` — a stamp/mark card that lives only in the catalog) are handled catalog-only: `refresh_card_prices` drops them from its upstream `id:"…"` query, and `get_card` never flags a variety row `refreshing` (there is no upstream price to re-fetch) and 404s an unknown variety id instead of proxying it. Smart-search parsing (tokenize → set-name match → quoting → word-drop fallback) is documented in HANDOFF "Smart search".
- `Backend/app/routers/auth.py` — register/login, JWT creation/validation (`mint_token` embeds a `tv` = `token_version` claim; `get_current_user` decodes, loads the user, and **rejects a token whose `tv` != the user's current `token_version`** — the revocation check, with a legacy no-`tv` token read as 0 so existing sessions survive the deploy), password rules. Registration also fires a verification email best-effort (see below). Both routes are per-IP rate-limited (login 10 attempts/5 min — counted whether they succeed or fail, so a brute-forcer's lucky guess is blocked too; register 10/hour) via `app/services/rate_limit.py`. A cluster of authed self-service account endpoints backs the Profile page: `GET /auth/me` returns the account fields (`user_info` — email, username, created_at, accepted_terms_at, the `email_verified` flag (`email_verified_at is not None`), plus the computed `is_admin` flag from `admin_access`; never the password hash); `PATCH /auth/me` updates email and/or username (only the fields sent are touched, each checked for uniqueness against *other* users so re-saving your own value is fine, email lightly format-validated by `valid_email`; **a changed email clears `email_verified_at` and re-sends a verification email** to the new address, best-effort); `POST /auth/me/password` changes the password (verifies the current one with `pwd_context.verify`, then applies `password_error`'s rules to the new one — rate-limited 10/5 min under a `"password"` scope as cheap defense in depth if a token is ever stolen), then **bumps `token_version` (revoking other sessions) and returns a fresh token** so the current device stays logged in. `POST /auth/me/sign-out-others` does that bump on demand — the leaked-token kill switch — also re-issuing a token for the caller; every other outstanding JWT 401s on its next request. `DELETE /auth/me` (authed) is self-service account deletion: it bulk-deletes the user's `portfolio_cards`, `portfolios`, `password_reset_tokens`, and `email_verification_tokens` first (none of those FKs has an `ON DELETE` cascade, so Postgres would otherwise reject the parent delete; lots go before portfolios), then the `User` row. The shared `card_price_snapshot` rows are per-card, not per-user, so they're intentionally left in place. **Password reset** (both unauthed): `POST /auth/forgot-password` takes `{email}` and always answers the same generic message whether or not the address has an account — only the inbox learns the difference (anti-enumeration; keep the responses identical). For a real account it mints a `secrets.token_urlsafe(32)` token, stores only its sha256 (`hash_token`) in `password_reset_tokens` with a 30-min expiry (`RESET_TOKEN_TTL_MINUTES`) — deleting any older tokens first, so one live link per account — and emails `FRONTEND_BASE_URL/reset-password?token=<raw>` via `app/services/mailer.py` (a send failure is logged and swallowed: the response must not change). Rate-limited 5/hour (`forgot` scope) since each valid hit sends an email. `POST /auth/reset-password` takes `{token, new_password}`: looks up the sha256, rejects missing/used/expired tokens with one uniform 400 ("This reset link is invalid or has expired — request a new one"), applies `password_error`'s rules (a weak password 400s *without* burning the token), then swaps the hash and stamps `used_at` (single-use). Shares the `password` 10/5min scope with the authed change-password route. A reset also **bumps `token_version`**, so it invalidates every existing JWT for that account (unlike before; the authed change-password does the same but re-issues one for the current tab). The reset email's styled HTML is `reset_email_html` here (dark palette inlined on table markup, entity-encoded, username escaped). **Email verification** (soft — the app works unverified): `send_verification_email` mints/stores a hashed single-use token in `email_verification_tokens` (24h, `VERIFY_TOKEN_TTL_HOURS`, one live per user) and emails `FRONTEND_BASE_URL/verify-email?token=<raw>` (`verify_email_html`); called best-effort from `register` and from `PATCH /auth/me` on an email change. `POST /auth/verify-email/send` (authed, 5/h `verify` scope) resends it (benign no-op once verified); `POST /auth/verify-email` (**unauthed** — the link works logged-out) consumes the token and stamps `email_verified_at`, same missing/used/expired handling as reset. **Social sign-in (OAuth/OIDC)** — Google + Microsoft, server-side Authorization Code + PKCE flow (no third-party JS on the page; the OIDC plumbing lives in `app/services/oauth.py`): `GET /auth/oauth/providers` lists only the **configured** providers (config-gated — a provider with no client id/secret env is invisible), so the frontend renders a button per entry; `GET /auth/oauth/{provider}/start` (rate-limited `oauth` 30/5min) 302s to the provider's consent screen (unknown/unconfigured → 404); `GET /auth/oauth/{provider}/callback` validates `state`, trades the code for a verified identity, resolves/merges the account, and 302s to `FRONTEND_BASE_URL/auth/callback#token=<jwt>` (token in the fragment, never logged), bouncing every failure to `FRONTEND_BASE_URL/login?oauth_error=<code>` (`cancelled`/`expired`/`provider_error`/`email_unverified`/`unavailable`). `resolve_oauth_user` is the **merge** core (importable + unit-tested): returning identity (provider+sub already linked) → that user; else a provider-**verified** email matching an existing account → link the provider to it (the requested MERGE, no duplicate) and stamp `email_verified_at`; else verified email with no account → create one; an **un**verified email colliding with an existing account is **refused** (`email_unverified` — no silent takeover). New OAuth users get a generated unique username, `accepted_terms_at` stamped (the button carries the terms line), and `hashed_password=None`. `user_info` now also returns `has_password` + `oauth_providers`; `login` and `POST /auth/me/password` guard a `None` password hash (a social-only user sets one via the forgot-password flow); `DELETE /auth/me` clears the user's `oauth_accounts` too.
- `Backend/app/routers/portfolio.py` — portfolio CRUD, named-portfolio management, batched price fetching, daily price snapshots, history endpoint. **Named portfolios:** `GET /portfolios` (default first, each with `card_count`; `ensure_default_portfolio` creates the default so the list is never empty), `POST /portfolios` (`{name}`, trimmed 1–60, 409 on a case-insensitive per-user name clash), `PATCH /portfolios/{id}` (rename), `DELETE /portfolios/{id}` (deletes the portfolio **and its lots** — no FK cascade; 400 if it's the user's only one). `_owned_portfolio` is the ownership guard (404 otherwise). Lot endpoints take an optional `portfolio_id`: add/add-batch resolve the target via `_resolve_target` (given id ownership-checked, else the default); `GET /portfolio` + `GET /portfolio/history` scope to it when present, but **omitted returns lots across ALL the user's portfolios** (the frontend's account-wide owned badge depends on this). `fetch_prices` resolves all held cards in one upstream OR-query (`id:"a" OR id:"b" …`, chunks of 100) and caches per-card prices for 15 minutes (`_price_cache`); `/portfolio/add` seeds that cache from the card it already fetched. **Prices come from every source, freshest first** (`_fallback_prices`): the live pokemontcg.io TCGplayer figure, then — for cards it returns unpriced (the newest sets it lags on, e.g. Ascended Heroes) — the real TCGplayer price the daily job seeded into the local `card_catalog` from TCGCSV, then the latest recorded `card_price_snapshot` (the daily job's eBay sold-median). So the portfolio tracks the same value the browse pages show instead of a blank price; the fallback is used by both `/portfolio` (current price + image, P&L, daily change) and `/portfolio/add`'s auto-price when no purchase price is given. Upstream stays the source of truth wherever it has a price — the fallback only fills the gap — and the cache/add flow store the *resolved* price (not a bare upstream `None`), so a later load can't read back a cached `None` and hide the fallback. A card whose upstream chunk fails and that no fallback can price stays uncached, so a transient upstream error retries next load. Each `/portfolio` row also carries a `price_change` (today vs the card's daily-change baseline, via `price_history.change_baselines`) and the card's real `image_url` (fetched alongside prices, same cache — never guess image URLs from card ids; see HANDOFF "Behaviors worth knowing"). Price/snapshot helpers live in `price_history.py`. Routes sit behind the shared `"api"` per-IP rate limit (120/min, one budget with the cards router). A **synthetic variety id** (a stamp/mark card that exists only in the catalog) is never sent upstream: `fetch_prices` skips it from the OR-query and prices it through `_fallback_prices` (catalog → snapshot), and `/portfolio/add` resolves it from the catalog (`card_catalog.get_card`) rather than the upstream single-card lookup — so a variety is fully holdable with correct P&L. `POST /portfolio/add-batch` is the scanner batch-mode bulk add: a list of up to 100 `{card_id, purchase_price?, quantity}` items. Every scanned id is a `card_catalog` row, so names resolve from the catalog (no per-card upstream GET) and auto-priced items (no `purchase_price`) resolve in ONE `fetch_prices` pass; per-item failures are reported, not fatal → `{added, failed: [{card_id, reason}], message}`. Both `/portfolio/add` and `/portfolio/add-batch` accept an optional `purchase_date` per item — set only by the Portfolio page's CSV import so a Mintly-exported backup restores each lot's original date; omitted (the scanner never sends it), the column's `default=utcnow` fires.
- `Backend/app/routers/scan.py` — `POST /scan`, the camera card scanner: takes an uploaded photo (`UploadFile`), embeds it with CLIP via `card_embed` (the image **and** its horizontal mirror, so a selfie-mirrored front camera still matches), finds the nearest catalog cards by cosine similarity (top 12), and returns them in the same paged `{data, page, pageSize, totalCount}` envelope as search — run through the same `annotate_price_changes`/`attach_estimates` so scan tiles render like search tiles. Each returned card also carries `matchScore` (the CLIP cosine, kept rather than discarded) so the frontend's batch mode can flag shaky best-guesses for review. A **sync `def`** so FastAPI runs the CPU-bound embedding in its threadpool (the api is a single worker). **Login-only** — a router-level `Depends(get_current_user)` gates the whole router, so an anonymous request 401s before any embedding runs (the scanner is an account feature: you scan to add to a portfolio). Own `scan` per-IP rate-limit scope (60/min — an abuse guard, not a usage cap: the feature is meant to be free and unlimited for real users). Returns `[]` until `card_catalog.embedding` is backfilled by `scripts/embed_catalog.py`.
